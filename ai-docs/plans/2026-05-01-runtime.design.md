# Design: Runtime & Object Tree

**Issue:** ai-docs/plans/2026-05-01-runtime.spec.md
**Date:** 2026-05-01

## Approach

### Ownership model decision: Arena (SlotMap)

The primary open question from the spec is whether to use an arena with
`SlotMap<InternalKey, Box<dyn Object>>` or pervasive `Rc<RefCell<dyn Object>>` handles.
**Arena is chosen.** Justification:

| Concern | Arena (SlotMap) | Rc<RefCell<>> |
|---|---|---|
| Aliasing / borrow conflicts | Single-owner store; callers hold `ObjectId` keys, never raw refs across mutations | Multiple `RefCell` borrows; `borrow_mut()` panics at runtime on re-entrant signal emit |
| Signal emit re-entrancy | Safe: emit borrows the slot list, then releases before calling each slot | Dangerous: emitting from a slot that holds a `RefCell` borrow is a runtime panic |
| Thread safety | `ObjectTree` behind `RwLock`; `ObjectId` is `Copy + Send` | `Rc` is not `Send`; would need `Arc<Mutex<>>` with coarser granularity |
| Performance | Cache-friendly slab allocation | Extra allocation per object; pointer-chasing |
| `WeakRef<T>` semantics | `ObjectId` key — staleness detected by presence in `ObjectTree`'s forward index (`contains(id)`) | `Weak<RefCell<T>>` — natural, but coupled to `Rc` lifetimes |
| Fit with Qt model | Qt's object tree is a central store; `ObjectId` ~ pointer address analogy | Less analogous; `Rc` lifetime is independent of the tree |

The one downside of the arena is that returning a `&T` from `ObjectTree::get()` ties a borrow to
the tree lock for the duration of the caller's use. This is resolved by a **closure-based API**:
callers pass a closure to `ObjectTree::with<R>(id, |obj: &dyn Object| -> R)` or
`ObjectTree::with_mut<R>(id, |obj: &mut dyn Object| -> R)`. Long-lived typed borrows are never
handed out publicly.

**Rejected: `Rc<RefCell<>>`**
The fatal flaw is signal-emit re-entrancy. A slot connected via `Direct` is called synchronously
during `emit`. If the slot mutably borrows a second object that is already borrowed by the call
stack, `RefCell::borrow_mut()` panics. This is not hypothetical — Qt's own re-entrancy model has
the same hazard in C++, and Qt resolves it via the event loop (`Queued` dispatch). With
`Rc<RefCell<>>`, `Direct` connections become a minefield. The arena model sidesteps this because
the store is reborrowed fresh per call.

### ObjectId reconciliation with quartzite-core

quartzite-core defines `ObjectId` as a newtype around `AtomicU64` (monotonic counter). SlotMap's
built-in key type is `(u32 index, u32 generation)` — incompatible as a type-level identity. The
runtime resolves this by keeping **both identities**:

- `quartzite-core::ObjectId` (u64) is the **logical, stable identity** used for naming, logging,
  `ConnectionTable` keys, and as the public API surface. quartzite-core allocates it.
- `slotmap::DefaultKey` is the **arena slot key** used only inside `ObjectTree` for O(1) access.
  It is stored in a private `HashMap<ObjectId, DefaultKey>` (forward index) kept inside
  `ObjectTree`. The runtime also maintains a reverse `HashMap<DefaultKey, ObjectId>` for
  `destroy` traversal.

`ObjectRef<T>` and `WeakRef<T>` both wrap `quartzite-core::ObjectId`. `WeakRef` is distinguished
by having no liveness guarantee — validity is confirmed by calling `ObjectTree::contains(id)`,
which checks presence in the forward index. This is consistent with quartzite-core's
`Value::Object(WeakObjectRef)` where `WeakObjectRef` is an opaque newtype filled in from the
runtime.

### WeakRef / WeakObjectRef alignment

quartzite-core's design defines `type WeakObjectRef = alloc::sync::Weak<dyn Object>` as a
placeholder. With the arena model, this type alias cannot stand — there is no `Arc<dyn Object>`
in scope. The core team must change `WeakObjectRef` to a newtype with a runtime-provided concrete
implementation:

```rust
// in quartzite-core (to be updated — see Task 0)
pub struct WeakObjectRef(pub u64);  // wraps ObjectId inner value
```

quartzite-runtime implements the staleness check: `ObjectTree::is_valid(WeakObjectRef)` delegates
to `ObjectTree::contains(ObjectId::from(weak.0))`. This keeps core no_std-safe and
runtime-agnostic. Task 0 (below) is the explicit prerequisite; Task 3 depends on it.

### Parent/children: single source of truth in ObjectTree

`ObjectBase` (quartzite-core) does **not** store `parent` or `children`. Those fields are removed
from `ObjectBase`. The **sole** source of truth for the parent-child relationship is `ObjectTree`,
which maintains:

- `HashMap<ObjectId, ObjectId>` — child → parent (parent map)
- `HashMap<ObjectId, Vec<ObjectId>>` — parent → ordered children list (children map)

`ObjectExt::parent()` and `ObjectExt::children()` delegate to a registered tree accessor rather
than reading from `ObjectBase`. Concretely, `Application` exposes a process-wide
`ObjectTree`-accessor function; `ObjectExt` calls it. This avoids any dual-update protocol and
eliminates the dual-source-of-truth hazard entirely.

Protocol for all tree mutations (`insert`, `reparent`, `destroy`) is:
1. Acquire write lock on `ObjectTree`.
2. Update the SlotMap and the forward/reverse identity maps.
3. Update the parent map and children map atomically in the same lock scope.
4. Release lock.

No caller ever mutates parent/children outside of `ObjectTree`'s locked methods.

### Queued dispatch: no_std policy

`Queued` connections require an event loop, which requires `std`. Therefore:

- `ConnectionType::Queued` is only available under `#[cfg(feature = "std")]`.
- In `no_std` builds, `Signal::connect` with `ConnectionType::Queued` is a **compile error**
  (achieved by making the `Queued` variant, or the relevant `connect` overload, `#[cfg(feature = "std")]` only).
- There is no silent fallback to `Direct` and no `eprintln!` call on any fallback path.
- This is the clean policy (option a): if you don't have `std`, you don't get queued connections.

---

### Queued dispatch: Signal/ConnectionTable integration

`Signal::emit` in quartzite-core handles `Direct` slots inline. For `Queued` connections
(available only under `feature = "std"`), core must not call `EventLoop::post` directly (that
would create a circular dependency: core → runtime). Instead, core defines a minimal seam trait:

```rust
// in quartzite-core, behind #[cfg(feature = "std")]
pub trait QueuedDispatcher: Send + Sync {
    fn post(&self, f: Box<dyn FnOnce() + Send>);
}
```

`ConnectionTable` in quartzite-runtime implements `QueuedDispatcher`. The runtime installs the
table as a global (same `OnceLock` as `Application`) so `Signal::emit` can call it via a
process-global accessor function also defined in core:

```rust
// in quartzite-core, behind #[cfg(feature = "std")]
static QUEUED_DISPATCHER: OnceLock<Arc<dyn QueuedDispatcher>> = OnceLock::new();

pub fn set_queued_dispatcher(d: Arc<dyn QueuedDispatcher>) { ... }
pub fn queued_dispatcher() -> Option<&'static Arc<dyn QueuedDispatcher>> { ... }
```

`Application::new()` registers the `ConnectionTable` as the dispatcher. Before `Application` is
created, `Queued` connections are silently dropped (no `eprintln!` — this is a documented
invariant, verifiable via `#[cfg(debug_assertions)]` tracing if desired in future).

This design:
- Keeps core no_std-safe (OnceLock is in `std`; gated behind `feature = "std"`)
- Avoids a runtime→core circular dep
- Makes the threading seam explicit and testable

### Signal thread-safety for queued dispatch

quartzite-core's `Signal<Args>` is not `Send + Sync` in the first iteration. Slots are
`Box<dyn Fn(&Args)>`. For `Queued` connections to work cross-thread, the slot invocation must be
packaged as a `Box<dyn FnOnce() + Send>`. This means:

- The `Args` value is cloned at emit time and moved into the closure (requires `Args: Clone + Send`
  for queued slots — documented constraint on the connection API).
- The `SlotEntry` for a `Queued` connection stores a `Box<dyn Fn(Args) + Send + Sync>` (note
  owned `Args`, not borrowed), separate from `Direct` slots.
- `Signal<Args>` itself remains local-thread-only; only the packaged closure crosses threads.

This is consistent with Qt's model: queued connections copy the arguments.

### ConnectionRecord and ReceiverGuard

Each active connection is represented by a `ConnectionRecord`:

```rust
struct ConnectionRecord {
    sender_id:      ObjectId,
    signal_index:   SignalIndex,
    receiver_id:    ObjectId,
    receiver_guard: Weak<ReceiverGuard>,   // captured at connect time
    slot:           SlotEntry,             // Direct or Queued variant
}
```

`receiver_guard` is populated at connect time by
`Arc::downgrade(&receiver.object_base().receiver_guard)`.

**Queued dispatch guard check:** before posting the closure to `EventLoop`, the dispatcher calls
`receiver_guard.upgrade()`. If it returns `None` (receiver has been destroyed and its
`Arc<ReceiverGuard>` has been dropped), the closure is silently discarded — it is never posted.
This prevents destroyed receivers from having queued slots invoked after destruction.

**Direct dispatch guard check:** `Signal::emit` already skips slots whose `Weak<ReceiverGuard>`
cannot be upgraded (per quartzite-core's existing design). No change needed there.

### ConnectionTable design

`ConnectionTable` is a process-wide singleton (`OnceLock<Arc<ConnectionTable>>`). It stores
active connections between signals and slots, keyed by `ConnectionId`.

```
ConnectionTable
  connections: RwLock<HashMap<ConnectionId, ConnectionRecord>>
  by_receiver:  RwLock<HashMap<ObjectId, Vec<ConnectionId>>>
  by_signal:    RwLock<HashMap<(ObjectId, SignalIndex), Vec<ConnectionId>>>
```

- Two secondary indices allow O(m) cleanup when an object is destroyed.
- Lock scope is minimal: grab a read lock to look up receivers, release it, then invoke slots
  outside the lock. This prevents deadlock during re-entrant emit.
- `DashMap` is deferred (YAGNI — no measured contention at this stage).

`connect_signal` procedure:
1. Allocate a `ConnectionId`.
2. Capture `Arc::downgrade(&receiver.object_base().receiver_guard)` into `ConnectionRecord.receiver_guard`.
3. Insert into `connections`, `by_receiver`, and `by_signal` under write locks.

### EventLoop design

`EventLoop` runs on the thread that calls `EventLoop::run()`. It blocks that thread. A
`std::sync::mpsc::Sender<Box<dyn FnOnce() + Send>>` channel allows any thread to post work.

```
EventLoop {
    sender: Sender<Box<dyn FnOnce() + Send>>,
    receiver: Receiver<Box<dyn FnOnce() + Send>>,
    running: Arc<AtomicBool>,
}
```

- `EventLoop::post(f)` clones the `Sender` and sends `f` — callable from any thread.
- `EventLoop::run()` drains `receiver` (non-blocking `try_recv` loop) then sleeps for a tick
  (configurable, default 1ms) or blocks on `recv_timeout` when idle.
- `EventLoop::stop()` sets `running = false` and sends a wake-up sentinel.
- `Application::exec()` is the canonical blocking entry point.
- `Application::post_event(f)` delegates to `EventLoop::post`.

### Application singleton

```rust
static APP: OnceLock<Arc<ApplicationInner>> = OnceLock::new();

pub struct Application(Arc<ApplicationInner>);

struct ApplicationInner {
    object_tree: RwLock<ObjectTree>,
    event_loop: EventLoop,
    connection_table: Arc<ConnectionTable>,
}
```

- `Application::new()` → `Result<Application, ApplicationError>`.
- Second call returns `Err(ApplicationError::AlreadyExists)`.
- `Application::global()` → `Option<Application>` for access without ownership.

### Timer design

`Timer` fires its `timeout` signal on a periodic interval using a dedicated background thread.
Because `Signal` is not `Send`, `timeout` is not emitted directly from the background thread.
Instead, the background thread calls `EventLoop::post(|| timer.fire())`, and `fire()` emits the
signal on the event loop thread.

```rust
pub struct Timer {
    base: ObjectBase,
    interval: Duration,
    single_shot: bool,
    handle: Option<JoinHandle<()>>,
    running: Arc<AtomicBool>,
    pub timeout: Signal<()>,
}
```

Timer start/stop are called from the event loop thread. The background thread holds an
`Arc<AtomicBool>` for cancellation and a `Sender` clone for posting.

---

### ThreadPool design

A basic fixed-size pool. No per-thread event loops. Workers run `FnOnce + Send` tasks.

```rust
pub struct ThreadPool {
    sender: Sender<Box<dyn FnOnce() + Send>>,
    workers: Vec<JoinHandle<()>>,
}
```

`ThreadPool::spawn(f)` sends `f` through the channel; workers pick it up. Shutdown on `Drop`
closes the sender and joins all workers.

### Key invariants

1. `ObjectTree` owns all objects via `SlotMap<DefaultKey, Box<dyn Object>>`.
2. A `HashMap<ObjectId, DefaultKey>` maps logical ids to arena slots (forward index).
3. A `HashMap<DefaultKey, ObjectId>` is the reverse (for destroy traversal).
4. A `HashMap<ObjectId, ObjectId>` tracks parent (child → parent).
5. A `HashMap<ObjectId, Vec<ObjectId>>` tracks children (parent → ordered children list).
6. `ObjectBase` does NOT store `parent` or `children`; maps 4 and 5 are the sole source of truth.
7. `destroy(id)` does a depth-first post-order traversal of the children map, removing slots
   and index entries. Stale `ObjectId`s simply resolve to `None` after removal.
8. `EventLoop::post(f)` sends `f` through mpsc; the loop thread drains the channel each tick.
9. Before posting a queued slot, `receiver_guard.upgrade().is_some()` is checked; if `None`, the
   closure is discarded without being posted.
10. `ConnectionTable` lock is never held during slot invocation — always released first.
11. `ConnectionType::Queued` is only available with `feature = "std"`. No silent fallback exists.

## Risks

- **`ObjectId` dual-identity complexity**: Maintaining two maps (`ObjectId→SlotKey` and
  `SlotKey→ObjectId`) adds bookkeeping and two failure modes (key present in one map but not the
  other). Mitigation: encapsulate both maps in a private `ObjectIndex` struct inside
  `object_tree.rs`; add debug assertions that both maps agree; covered by unit tests in Task 4.

- **Re-entrancy during `destroy`**: A slot triggered by a signal might call `destroy` on an
  object. If `ObjectTree` is locked write-exclusively at that moment, this deadlocks.
  Mitigation: `destroy` acquires a write lock. Slots must not hold the tree lock when calling
  `emit`. Document this as an invariant; enforce by never providing a public `&mut ObjectTree`
  to user code directly.

- **ObjectTree borrow and signal emit re-entrancy**: A `Direct` slot call during `emit` may
  attempt to call `ObjectTree::insert` or `destroy` while the tree is locked.
  Mitigation: tree lock is `RwLock`; `with` acquires a read lock; `with_mut`/`destroy` acquire
  write locks. Slots must complete before the next write lock can be acquired. Queued connections
  avoid this entirely by deferring to the event loop.

- **Task 0 blocking all runtime work**: Removing `parent`/`children` from `ObjectBase` and
  changing `WeakObjectRef` are breaking changes to quartzite-core. All runtime tasks depend on
  Task 0 completing first. Mitigation: treat Task 0 as a separate, small, mergeable PR with clear
  acceptance criteria so it does not block the runtime implementation for long.

- **`Signal` not `Send+Sync`**: Slots are `Box<dyn Fn(&Args)>` without `Send`. Queued dispatch
  requires `Args: Clone + Send`. Mitigation: document constraint on connection API; queued
  connections store a separate `Box<dyn Fn(Args) + Send + Sync>` slot variant (owned args).
  This is an additive change to `Signal`; does not break `Direct` slots.

- **Timer accuracy on loaded systems**: `std::thread::sleep` has OS-level jitter.
  Mitigation: AC7 uses a generous 200ms window for a 50ms interval — acceptable for v1.
  Precision timing is deferred.

- **Application singleton in tests**: Tests in the same process share the `OnceLock`.
  A second `Application::new()` in a subsequent test will fail.
  Mitigation: integration tests for `Application` live in `tests/application.rs` as a separate
  binary (each `tests/*.rs` file in Cargo is its own binary). Alternatively, a
  `#[cfg(test)] fn reset_for_test()` can be provided behind a feature flag.

- **`EventLoop::run()` blocks the caller**: Users must spawn a thread or use `exec()` correctly.
  Mitigation: document clearly; `Application::exec()` is the canonical entry point that blocks
  `main`; tests use a background `std::thread::spawn`.

## Open questions

- **`QueuedDispatcher` trait location**: Proposed to live in quartzite-core behind `feature = "std"`.
  Alternative: define it in quartzite-runtime and have core use a raw function pointer or a
  `OnceLock<fn(Box<dyn FnOnce() + Send>)>`. The trait approach is cleaner but adds a core→std
  dependency for the feature. Needs decision before Task 5.

- **`ObjectFactory` global vs. per-`Application`**: The spec says `ObjectFactory::create` is used
  by scripting/serialization. Should there be a process-wide factory singleton (like
  `ConnectionTable`), or one per `Application`? **Proposed**: per-`Application`, accessible via
  `Application::factory()`.

- **`ThreadPool` shutdown semantics**: Should `ThreadPool::drop` wait for in-flight tasks to
  complete (graceful) or abandon them? **Proposed**: graceful — close the sender and join all
  workers. Panic in a worker thread propagates as a resumed panic in `join()`.

- **`ObjectExt::parent()` / `children()` accessor mechanism**: With parent/children removed from
  `ObjectBase`, these methods need to reach `ObjectTree`. The simplest approach is a
  process-global `fn with_tree<R>(f: impl FnOnce(&ObjectTree) -> R) -> R` registered by
