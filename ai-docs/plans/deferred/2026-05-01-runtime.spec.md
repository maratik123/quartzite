# Runtime & Object Tree

**Source:** AI design dialogue (tmp/qt_01..14.log)
**Date:** 2026-05-01

## Scope

Implement `quartzite-runtime` crate. Requires `std`. Builds on `quartzite-core`.

- `ObjectTree` — central store for all objects; manages parent-child relationships and lookup by name/id
- `ObjectRef<T>` / `WeakRef<T>` — typed handles into the tree
- `Application` — singleton entry point; owns ObjectTree and EventLoop
- `EventLoop` — runs the main loop; dispatches queued slot calls and timer events
- `ConnectionTable` — global store of active connections; used by `Signal::emit` for queued dispatch
- `ObjectFactory` — create objects by class name string (used by scripting / serialization)
- `Timer` — fires a signal at a given interval
- `ThreadPool` — worker threads for compute tasks (basic; not event-loop threads)

## Out of scope

- Widget rendering (quartzite-widgets)
- Event model types (quartzite-events)
- Python interop (deferred)

## Deferred

- Multi-window support | needs platform backend first
- Thread event loops (one loop per thread) | defer until threading model decided
- `BlockingQueued` connection type | depends on per-thread loops

## Key decisions

| Question | Decision |
|---|---|
| Object ownership model | **Open question** — this crate is where the decision lands; must choose arena (SlotMap) or Rc<RefCell<>> before implementation begins |
| ConnectionTable scope | Global (process-wide) singleton, protected by Mutex |
| Timer backend | std::thread::sleep + background thread for now; async-compatible later |
| Application singleton | Enforced at runtime (panic if two created); stored in thread-local or global |

## Technical constraints

- Depends on `quartzite-core`; no dependency on `quartzite-macros`
- `ObjectTree::destroy(id)` must recursively destroy children in depth-first order
- `ConnectionTable` must be lock-free or use short critical sections to avoid deadlocks during signal emit
- `EventLoop::post(fn)` must be callable from any thread (used by Queued connections)

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | `ObjectTree::insert(obj, parent_id)` returns an `ObjectId`; subsequent `get(id)` returns the same object |
| AC2 | `ObjectTree::destroy(id)` removes the object and all its descendants from the tree |
| AC3 | After `destroy(id)`, `get(id)` returns `None` |
| AC4 | Setting a parent-child relationship via `ObjectTree` is reflected in `obj.parent()` and `parent.children()` |
| AC5 | `ObjectTree::find_by_name("foo")` returns the id of the object whose `object_base().name == "foo"` |
| AC6 | `EventLoop::post(f)` called from a different thread causes `f` to execute on the event loop thread |
| AC7 | `Timer` with 50ms interval emits its `timeout` signal at least once within 200ms of being started |
| AC8 | `ObjectFactory::create("ClassName")` returns a `Box<dyn Object>` for a previously registered class |
| AC9 | `Application::new()` succeeds exactly once per process; a second call panics or returns `Err` |

## Open questions

- **Object ownership**: arena (SlotMap + ObjectId keys) vs `Rc<RefCell<dyn Object>>`? This is the primary decision blocking implementation.
- Should `ObjectRef<T>` be a typed wrapper around `ObjectId` or around `Rc<RefCell<T>>`?
- Should `ConnectionTable` use `DashMap` (lock-free) or `Mutex<HashMap>`?
- Should the event loop be `async`-runtime-agnostic (pluggable executor) or std-thread-based only?
