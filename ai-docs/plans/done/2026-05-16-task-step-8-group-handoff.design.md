# Design: /task Step 8 — every-group handoff redesign

**Issue:** #375
**Spec:** [`ai-docs/plans/2026-05-16-task-step-8-group-handoff.spec.md`](2026-05-16-task-step-8-group-handoff.spec.md)
**Date:** 2026-05-16

## Goals

- Replace the runtime `N=3 of M≥5` handoff gate in `/task` Step 8 with an **every-group** contract: each design-defined group runs in a fresh `/context-reset` subagent regardless of group position (first / middle / terminal) or total subtask count `M`.
- Make the orchestrator a **pure orchestrator during Step 8**: spawn group handoff → read returned progress-file delta → re-validate state → spawn next group's handoff. No subtask code is written in the orchestrator's own context during Step 8.
- Require a `## Handoff plan` section in **every** design document for `M ≥ 1`. Remove the `M ≤ 4 OPTIONAL` carve-out from both `design.md` and `design-review.md` in lockstep.
- Update `/context-reset`'s trigger wording (When triggered, `when_to_use`, "Maximum 3 handoffs per task" line) and widen its `allowed-tools` to cover the orchestrator-side bookkeeping the every-group contract makes routine.
- Widen the Task/Design Propagation Rule sync group in `AGENTS.md` to include `context-reset/SKILL.md` (the round-1-review-discovered meta-change — see § *DK-1 (revised)*) and extract one Propagation Rule row into `ai-docs/agent-writing-style.md` to stay under the 40,000-char hard cap (§ *DK-9*).
- Keep Steps 9 (verify) / 10 (self-review) / 11 (review fixes) in the orchestrator's own context. The redesign's fan-out covers Step 8 only.
- Capture the PR #374 context-rot incident in `ai-docs/learnings.md` (in-flow capture during this `/task`, `Escalated? no`).

## Non-goals

- **Pinning the `/task` orchestrator to a specific model.** Per spec Key Decision Q3, orchestrator model selection remains per-invocation. The redesign documents this as an explicit non-decision in `/task SKILL.md` Step 8 so future readers don't re-litigate.
- **Moving Steps 9–11 into dedicated handoff subagents.** Per spec Key Decision Q2 they stay in the orchestrator's own context. (Deferred-table entry covers the possible future move if compaction starts hitting Steps 9–11.)
- **Touching `/code-review`, `/pr-commented`, `/pr-ci-failed`, `/master-ci-failed`, `/bugfix`.** Grep audit (§ *Cross-skill grep audit*) confirms zero `N=3 / M ≥ 5` hits in those skill bodies — no cross-reference cleanup needed.
- **Changing `progress-format.md`.** The per-group subagent inherits the existing canonical schema verbatim (spec Key Decision: "Progress-file write contract").
- **Spec Key-Decision changes.** All Key Decisions in the spec are adopted as-is; the design only resolves Open Questions 1–6 and the round-1-review-discovered AGENTS.md sync-group expansion. **No Spec Amendment recipe is triggered:** spec § Technical Constraints explicitly anticipates an AGENTS.md edit ("if AGENTS.md must change, keep under 40k") and spec § Out of scope does not list AGENTS.md as untouchable — the round-1 design's "no AGENTS.md edit" claim is a Key-Decision flip inside the design's own scope, not a spec violation.

## Approach

### Why every-group fan-out works

PR #374's context-rot incident happened because one long-lived orchestrator session was carrying the entire workflow's prompt history through Step 8's 10 subtasks. Auto-compaction summarised the session, the summary dropped strict-sequence semantics (Steps 9–10 skipped, N=3 gate missed), and the post-compaction session continued silently in a degraded state.

The fix is **structural**: every subtask group runs in its own short-lived subagent invocation, the orchestrator does no Step-8 implementation work itself, and the orchestrator's own context never grows long enough to trip compaction. Steps 9–11 stay in the orchestrator because they are short-bounded (verify list ≈ 10 commands; self-review one subagent spawn; review-fix loop bounded to 3 rounds).

PR #372's pre-computed `## Handoff plan` already moved the *boundary representation* into the design document. PR #374's experience showed that representation alone wasn't enough — the orchestrator still consumed the work in-context. The every-group rule turns the design's `## Handoff plan` from a runtime advisory into a **mandatory fan-out spec**.

### Rejected alternatives

1. **Auto-detect compaction in the orchestrator and spin up a fresh top-level orchestrator session on demand.** Deferred (spec Deferred-table item 1). Would require telemetry the harness does not expose today; cannot detect "approaching" compaction reliably from inside the model. Discarded for now — the every-group rule eliminates the compaction trigger structurally without needing detection.
2. **Move Steps 9–11 into their own handoff subagent too.** Discarded for v1 (spec Key Decision Q2 + Deferred-table item 3). The user's original phrasing implied this; round-1 interview narrowed scope. Revisit only if Steps 9–11 are observed to trigger compaction in practice.
3. **Keep the `N=3 of M≥5` gate but also fan out the first group manually for all M.** Hybrid — rejected. Two coexisting rules (every-group fan-out AND runtime N=3 gate) double the cognitive cost without removing the runtime-gate failure mode that the PR #374 incident demonstrated. The clean rule is "every group fans out; no runtime gate". Pre-publish API stability (AGENTS.md § *API Stability*) authorises the clean break.
4. **Implement a `SessionStart|compact` hook.** Explicitly rejected upstream (spec Out-of-scope, citing `/context-reset SKILL.md § Why a callout at all`). Heuristic self-detection callouts stay the only mechanism.
5. **(Round-1 design) "No AGENTS.md edit; Propagation Rule already authorises the sync-group edits."** Rejected on round-1 review (Issue 1). The three existing Task/Design rows in AGENTS.md (lines 206–208) name only the triad `task/SKILL.md` ↔ `design.md` ↔ `design-review.md`; `context-reset/SKILL.md` is **absent** from all three rows' right-hand-sides. Because this PR changes the trigger contract that `context-reset/SKILL.md` carries (§ DK-4 + DK-3 + DK-2), `context-reset/SKILL.md` must be wired into the Task/Design sync group's Propagation Rule rows. Skipping the edit would leave the sync-group expansion undocumented; a future Task/Design edit would forget `context-reset/SKILL.md` and silently drift.

### Key design decisions (resolving spec Open Questions 1–6 plus round-1-review discoveries)

- **DK-1 (revised) — AGENTS.md edit IS required (round-1 review Issue 1).** Round-1's "no AGENTS.md edit" claim was false. The Task/Design Propagation Rule must be widened in two parts:
  - **(a) Widen each existing Task/Design row's right-hand side** (`AGENTS.md` lines 206, 207, 208) to include `context-reset/SKILL.md` alongside the existing triad members. After the edit, each row's right-hand side names the other two triad members **and** `context-reset/SKILL.md`. The parenthetical group label remains `(Task/Design group)`.
  - **(b) Append a new row** keyed on `.claude/skills/context-reset/SKILL.md`, listing the three siblings (`task/SKILL.md`, `design.md`, `design-review.md`) as propagation targets. New row sits immediately after the three Task/Design rows (after line 208) for visual cohesion. Group label: `(Task/Design group — context-reset trigger contract co-evolves with the sync group)`.
  This is a meta-change to the Propagation Rule itself. The implementing PR cannot succeed without it; **subtask 3** covers the row-widening + new-row append (round-2 review Issue 1 binds the order: subtask 2 = extraction, subtask 3 = row-widening, so AGENTS.md stays < 40k at every per-subtask commit — see DK-9).
- **DK-2 (revised) — `/context-reset` `allowed-tools` widening (spec Open Q #2; round-1 review Issues 4 + 5).** The per-group subagent runs `general-purpose` and inherits its toolset; the **skill body**'s `allowed-tools` governs only what the skill itself runs at the handoff seam. Under the every-group contract the seam runs: pre-handoff verification (`cargo build` + the full gate set), git state inspection (`git status`, `git rev-parse HEAD`, `git branch --show-current`, `git diff --quiet` / `git diff --stat`), progress-file edits (no Bash tool needed — Edit/Write), and the `Agent` spawn (no allow-list gating). The widening is therefore modest:
  ```
  allowed-tools: Bash(cargo build) Bash(cargo test *) Bash(cargo clippy *) Bash(cargo fmt *) Bash(cargo doc *) Bash(git status) Bash(git rev-parse *) Bash(git branch *) Bash(git diff *) Bash(git add *) Bash(git commit *)
  ```
  **Inclusion of `Bash(git diff *)`** (round-1 Issue 4): the handoff seam runs `git diff --quiet` / `git diff --stat` between group returns to validate the "no uncommitted dirt" requirement that subtask 4 names; the orchestrator's frontmatter already grants `Bash(git diff *)` (`task/SKILL.md` line 6), so granting it to the seam keeps the two contracts symmetric.
  **Exclusion of `Bash(git push *)`** (round-1 Issue 5): per `/context-reset/SKILL.md` line 80 (*"1 Agent = 1 subtask"*), the handoff seam does NOT push between subtasks. `git push *` is a Step 12 action, not a per-group seam action. Granting it to the seam would contradict the seam's no-push contract and weaken defence-in-depth. The orchestrator retains `Bash(git push *)` for Step 12; the seam doesn't need it.
  The `gh` family is NOT added — `/context-reset` does not interact with GitHub during a handoff seam. The Edit/Write tools and Agent spawning are not gated by `allowed-tools` (they are first-class tools, not Bash patterns), so no entry is needed for them.
- **DK-3 — `/context-reset` "Maximum 3 handoffs per task" line (spec Open Q #3).** **Rephrase**, do not remove. New wording: `Maximum 3 design-defined groups per task. If more needed — the task is too large, decompose into separate issues.` Removing the line drops a load-bearing upper bound (3 groups × 3 subtasks = 9 subtasks max, which already aligns with `design.md`'s "> 7 tasks → propose split"). Rephrasing preserves the cap while making it dimensionally correct under the every-group contract.
- **DK-4 — `when_to_use:` frontmatter (`/context-reset`).** Currently: *"Activate automatically after completing 3rd subtask when total >= 5, when a summary/compaction block appears at the top of context, or when noticing yourself rushing, simplifying, or skipping steps."* New wording: *"Activate at the start of every design-defined group per the design's `## Handoff plan`, when a summary/compaction block appears at the top of context, or when noticing yourself rushing, simplifying, or skipping steps."* Removes the `3rd subtask / total >= 5` clause; keeps compaction-detection and rushing heuristics.
- **DK-5 — Step 10 spawn-site audit (spec Open Q #4).** `grep -n 'spawn .*self-review\|self-review.md' .claude/skills/task/SKILL.md` returns matches at Step 10 only. No site implicitly assumed Step-8 work was inline (Step 10 reads spec / design / progress paths — all of which are produced by the per-group subagents and persist on disk). **No change needed at Step 10.** This is documented in the design's *Risks* section so a future reader doesn't re-investigate.
- **DK-6 — Progress-file delta parsing (spec Open Q #5).** **Free-form orchestrator read**, not formalised. The canonical schema at `ai-docs/templates/progress-format.md` is the source of truth either way; the orchestrator reads `current_step`, `last_passed_gate`, and the tail of the `Decisions log` between group returns and re-validates state (`base_commit` unchanged in the *header*, `git branch --show-current` unchanged, `git diff --quiet` returns clean). Formalising a delta-parser is premature (YAGNI) — the canonical schema already pins field names and write boundaries.
- **DK-7 — Cross-skill grep audit (spec Open Q #6).** Enumerated below (§ *Cross-skill grep audit*). Every live hit is rewritten in the implementing PR; every historical / spec-record hit is labelled as superseded.
- **DK-8 — Per-skill 5,000-token cap.** `wc -c` on every modified instruction file pre-edit:
  ```
  AGENTS.md                                         39775  (subtask 2 extracts first; subtask 3 widens on top)
  .claude/skills/task/SKILL.md                      20975
  .claude/skills/task/reference.md                  27984

  ```
  None of the SKILL.md / agent.md files are over the 35,000-char early warning. Step 8 sub-step 5's body shrinks (the multi-clause "N=3 / cross-check / Design Amendment / cite reference" paragraph collapses to a single every-group sentence + cite). Net delta is expected slightly **negative** for `task/SKILL.md`. AGENTS.md after subtasks 2 + 3 is described in DK-9.
- **DK-9 — AGENTS.md char-cap interaction (round-1 review Issue 2; round-2 review Issue 1 — per-commit ordering).** AGENTS.md is at 39,775 chars pre-task. The Propagation Rule widening alone would add ~250–400 chars (three rows gain `AND .claude/skills/context-reset/SKILL.md` each, plus one ~150-char new row), pushing the file to ~40,025–40,175 chars — **over the 40,000-char hard cap** that AGENTS.md's own AXIOM defines. Per the AXIOM ("≥ 40,000 chars → STOP; plan extraction"), the implementing PR must perform an extraction in the same change. **Round-2 review Issue 1 added a stricter constraint:** because `/task` Step 8 commits *per subtask* (not per group), AGENTS.md must stay < 40,000 at **every per-subtask commit boundary** within Group A, not just at the group's terminal commit.
  **Extraction target: AGENTS.md line 212**, the long single row keyed on `ai-docs/agent-writing-style.md` (596 chars including the leading `> `). The row's body — describing how new `## Patterns` entries in `agent-writing-style.md` cascade to downstream `.claude/agents/**` / `.claude/skills/**` consumers — is *about* `agent-writing-style.md`; moving it into `agent-writing-style.md` itself keeps the rule with its subject. Leave a one-line stub in AGENTS.md (~110 chars) pointing readers at `ai-docs/agent-writing-style.md § Propagation rule for new patterns`.
  **Per-commit arithmetic (subtask ordering: extraction first, then widening).** Round-2 review Issue 1 binds the order: subtask 2 = extraction, subtask 3 = row-widening. Stated explicitly so any future reader can verify no per-subtask commit crosses 40k:
  - **Pre-task:** AGENTS.md = 39,775 chars.
  - **After subtask 1 commit** (touches `.claude/agents/design.md` only; AGENTS.md untouched): AGENTS.md = 39,775 chars. ✓ < 40,000.
  - **After subtask 2 commit** (extraction: AGENTS.md line 212 ~596 chars → `ai-docs/agent-writing-style.md`; one-line stub ~110 chars left in AGENTS.md): AGENTS.md ≈ 39,775 − 596 + 110 = **≈ 39,289 chars**. ✓ < 40,000.
  - **After subtask 3 commit** (Propagation Rule widening: three existing rows gain `AND .claude/skills/context-reset/SKILL.md` each, +~250–400 chars total combined with a new ~150-char row keyed on `context-reset/SKILL.md`): AGENTS.md ≈ 39,289 + 250..+400 = **≈ 39,539..39,689 chars**. ✓ < 40,000.

  Net AGENTS.md delta after subtasks 2 + 3: `−486 (extraction) + 250..+400 (row widening) = −236..−86 chars`, comfortably back under 40,000 at every commit boundary. (The "≈ 39,338 chars after subtask 2" and "≈ 39,703 chars after subtask 3" figures cited in the round-2 review verdict assume slightly different per-row widening sizes; both estimates are well within the < 40k requirement either way.) This adopts the same model PR #324 used for the original AGENTS.md size reduction (extract verbose subsections into a topical reference page with a stub).
  **§ Enforcement cohesion fix (round-2 review Issue 2).** After the extraction lands in `ai-docs/agent-writing-style.md § Propagation rule for new patterns`, the file's existing § Enforcement section (lines 188–191) still says *"already covered by `AGENTS.md` `## Propagation Rule` — the row for `ai-docs/agent-writing-style.md` instructs editors to grep…"* — which now points at a stub that just points back into the same file (circular). Subtask 2's body therefore also amends § Enforcement to **replace the cross-reference into AGENTS.md with an intra-file reference to the new § Propagation rule for new patterns section**. (Reference-and-redirect chosen over collapse: § Enforcement's surrounding paragraphs talk about the forward direction of fan-out audit AND the `/ai-audit` reverse-direction sweep; collapsing the cross-reference paragraph into the new § Propagation rule section would commingle two distinct enforcement axes. A targeted in-place reference rewrite keeps both sections cohesive.)
  **Spec Amendment decision (round-1 review Issue 2 explicit ask):** **No Spec Amendment recipe is triggered.** Spec § Technical Constraints already anticipates the case verbatim — *"`AGENTS.md` is currently 39,775 chars… If this spec's implementation requires an AGENTS.md edit (e.g. AXIOM-level wording for the every-group rule), the implementer must keep AGENTS.md under 40,000 chars — extract verbose subsections into `ai-docs/<topic>.md` if needed (the model PR #324 used for the original AGENTS.md size reduction)."* The spec's existing wording already permits this design change; flipping DK-1 + adding DK-9 is a Key-Decision flip within the design's scope, not a spec violation.

## Risks

- **R1 — Step 8 sub-step 5 rewrite drifts from the spec's intent.** The new wording must explicitly cover four points: every group fans out; first group included; M = 1 included; orchestrator does NO Step-8 code itself. Mitigation: AC2's grep (`every group | first group | including the first`) acts as a mechanical check that all four phrasings land; AC11's negative grep (`N == 3 | N=3 | 3rd of M`) confirms the prior regime is fully removed. Subtask 5 self-validates against these two greps before commit.
- **R2 — `/context-reset` `allowed-tools` widening breaks a hidden invariant.** The current `Bash(cargo build)`-only narrow set may be deliberate (defence-in-depth: the handoff seam should not have powerful tools). Mitigation: the widening is minimal (DK-2 revised) — `cargo` family + `git` family (excluding `git push *` per round-1 Issue 5) + `git diff *` (per round-1 Issue 4); no `gh` family. The widening matches what `/task` SKILL.md already grants minus the no-push exclusion, so the seam never has *more* power than the orchestrator that invokes it, and strictly less than the orchestrator's Step-12 power. Documented in the design body so a future reader sees the explicit comparison.
- **R3 — Step 10's `self-review` spawn site implicitly assumed Step-8 work was inline.** Audit (DK-5) confirms it doesn't: Step 10 reads files from disk, not from in-memory context. The per-group subagents produce all artefacts on disk before returning. Mitigation: subtask 7 adds the per-group write-contract paragraph to `context-reset/SKILL.md § Handoff protocol`; subtask 9 verifies AC8 by grepping for that paragraph.
- **R4 — Per-group subagent boundary disagreement: orchestrator says "group complete" but the subagent's progress-file delta shows a gate failure.** Inherited from the existing per-step retry contract (spec Key Decision: "Failure handling"). Surface to user after 3 rejected attempts at the same group with the classic three options (retry / amend design / abort). No new failure mode the redesign introduces beyond what's already covered.
- **R5 — AGENTS.md char-cap proximity (39,775 chars pre-task).** Mitigated by DK-9 + the round-2-review-mandated subtask ordering: subtask 2 (extraction) precedes subtask 3 (Propagation Rule widening), so AGENTS.md is *first* reduced to ~39,289 chars and *then* grown to ~39,539..39,689 chars. - **R6 — Per-skill 5,000-token cap on `task/SKILL.md`.** Mitigated by DK-8: Step 8 sub-step 5 shrinks net (the every-group sentence is shorter than the multi-clause `N=3` paragraph it replaces). Subtask 9's `wc -c` audit confirms no SKILL.md crosses 35k.
