# Design: Unsafe Index (mirror of panic-index)

**Issue:** #420
**Tracked in:** #420
**Date:** 2026-05-16
**Revision:** Round 2 (spec amended — second initial-population site corrected from `wrapped_handler.rs:255` to `window_registry.rs:160`; Round-1 spec/code disagreement resolved by spec amendment, not by design unilaterally; symmetry follow-up retained as the sole § Open questions item)

## Approach

Mirror the existing panic-index machinery one-to-one onto a new `ai-docs/unsafe-index.md` artefact and wire five touchpoint files (per spec § Scope item 3) so every PR that introduces a new production `unsafe { … }` block or `unsafe fn` declaration is gated on a matching index entry.

**Why mirror, not extend or merge:** The user's spec § Key decisions row "New file or merge into panic-index?" already settled this — user explicitly asked for a parallel file. A merged "invariant-index" was the alternative considered and rejected (spec § Out of scope last bullet). A parallel artefact also lets the per-entry schema diverge cleanly (panic-index needs "Trigger / Why not `Result`"; unsafe-index needs "Why unsafe / Safety invariant / Why not safe Rust") without contorting one table to carry both shapes.

**Why one-to-one structural mirror, not a leaner schema:** panic-index has been live for several months, the 5-field per-entry table reads well, and the existing skill/agent bullets already follow a stable phrasing pattern. Reusing the exact shape means reviewers (human and `review-findings`/`self-review` agent) carry zero new mental model — they apply the panic-index check, swap the keyword, done. Diverging now would create two skill-bullet conventions that drift over time. Considered and rejected: a slimmer 3-field "Location / Justification / Preferred fix" schema — too compressed; "Why unsafe" and "Safety invariant" are genuinely different questions a reviewer needs the index to answer independently.

**Why review-time gate, not script gate:** Spec § Out of scope third bullet — script enforcement is deferred to a follow-up if/when manual review fails to catch a regression. Symmetric with panic-index, which has no `scripts/check-panic-index.sh` today. The `review-findings` and `self-review` bullets are the enforcement surface in v1.

- `quartzite-renderer/src/window_registry.rs:160` — `let event_loop = unsafe { &*ptr };` inside `WindowRegistry::try_create_window`. Raw-pointer deref of the `active_loop: Cell<*const ActiveEventLoop>` slot after a null check (`ptr.is_null()` at line 152 returns `Err(RendererError::OutsideCallback)`). The source already carries:

The four invariants: set-clear bracket maintained by `WrappedHandler` + `ActiveLoopGuard::Drop`; `!Send + !Sync` enforced by the raw-pointer field plus a `PhantomData<*const ()>` marker; the resulting shared reference lives only for the function body; null check precedes any deref. **Rejected alternatives:**

- **Extend panic-index.md with a second `## Active entries (unsafe)` section.** Rejected: spec explicitly asks for a parallel file; mixing concerns in one file weakens grep ergonomics ("does this file track panics, unsafe, both?") and bloats the per-entry schema.
- **Use a generated index** (parse `# Safety` doc sections + `rg` hits, emit table). Rejected: panic-index is hand-curated for a reason — the narrative "why not safe Rust / preferred fix" columns are inherently human-authored; a generated index would need the same fields anyway, just as commit-time metadata.
- **Add the index but skip the review-findings + self-review wire-up in v1.** Rejected: without the sync gate, the index drifts within one PR cycle. The gate IS the deliverable; the file is the artefact the gate enforces.
- **Use `wrapped_handler.rs:255` as the second initial-population site (Round-1 spec literal).** Rejected (and resolved by the Round-1 → Round-2 spec amendment). That line sits inside `#[cfg(test)] mod tests` (cfg attribute at line 222 of `wrapped_handler.rs`), so under the spec's own § Out of scope item 2 it is explicitly NOT a production unsafe and MUST NOT receive an index entry. Round-1 design-review surfaced the disagreement; the user adjudicated via spec amendment and chose `window_registry.rs:160` as the corrected second site (a real production unsafe with a four-invariant `# Safety invariants` doc block and an inline `// SAFETY:` comment in the source). This design (Round 2) honours the amendment.

## Risks

- **Risk: the `rg` exclude pattern for `#[cfg(test)]` is line-based and cannot reliably detect "this `unsafe {` line is inside a `#[cfg(test)] mod tests { … }` block".** Panic-index documents the same limitation implicitly (its recipe uses a plain grep with no module-aware filter). *Mitigation:* the recipe documented in subtask 3 names the limitation explicitly — `rg '\bunsafe\s*\{|\bunsafe\s+fn\b' <changed-files>` is the catch-net; humans/agents must walk hits and confirm module context. The `^\s*///\s*#\s*Safety` primary signal sidesteps the issue (doc sections on `unsafe fn` and `unsafe trait` are inherently scoped to declarations the reviewer reads in full). Concrete consequence on AC7: the bare grep returns `wrapped_handler.rs:255` (test-only); the reviewer walking hits confirms it sits inside `#[cfg(test)] mod tests` (cfg attribute at line 222) and skips it. Same recipe panic-index uses for its own test-only sites.
- **Risk: file-size axiom breach on touchpoint files after edit.** Per spec § Technical constraints, all 4 touchpoint instruction files have ≥ 6,000 chars of headroom under the 35k early-warning band; the per-file edit adds ≲ 400 chars in the worst case (subtask 3 on reference.md, which receives a full new H2 section). *Mitigation:* the verify step (subtask-level) re-runs `wc -c` on each edited file before commit. AC8 enforces this at Step 9. The amendment does not change any touchpoint-file edit size — the substitution lives in subtask 1's new `unsafe-index.md` body, not in any of the AC8-budgeted files. No file crosses 35,000 chars.
- **Risk: drift between panic-index bullet phrasing and unsafe-index bullet phrasing on future skill/agent edits.** *Mitigation:* the existing AGENTS.md Propagation Rule fires on any edit to `.claude/skills/**` or `.claude/agents/**` — the grep step naturally surfaces both index bullets so they get co-edited. No new sync-group row is needed (spec § Scope item 4 default). The unsafe-index bullets are written immediately adjacent to the panic-index bullets in each file, so a reviewer scanning either file sees both at once.
- **Risk: `window_registry.rs:160` entry contradicts the existing in-source narrative bodies.** The source already carries (a) a `# Safety invariants` doc block on the `active_loop` field spanning `window_registry.rs:66–84` (H3 heading at line 66, four numbered invariants at lines 68–80, intra-doc-links at 82–83) and (b) an inline `// SAFETY:` comment at lines 155–159 restating the same four as a checklist directly above the `unsafe { &*ptr }` line. The index entry's **Why unsafe** / **Safety invariant** / **Why not safe Rust** / **Preferred fix** fields restate or cross-link to those bodies; any divergence creates three drifting sources of truth (doc block, comment, index entry). *Mitigation:* subtask 1's acceptance — reinforced in subtask-1's body — is that the entry's **Safety invariant** field is phrased as a cross-reference to the canonical sources (`window_registry.rs:66–84` doc block + `window_registry.rs:155–159` inline comment), not a duplicate enumeration; the Why-not-safe-Rust field explains why winit's `ActiveEventLoop` cannot be held across the callback boundary as a safe reference (lifetime is bound to the winit callback frame, not to `WindowRegistry`). Reviewer cross-checks the index entry against the doc block as part of AC2's "substantive content" criterion. Cross-reference phrasing (rather than duplication) is the structural mitigation: a single canonical source per invariant.
- **Risk: pre-publish AXIOM ("no compat shims") suggests removing panic-index sync surface and replacing wholesale.** *Mitigation:* the AXIOM applies to Rust public API in `cargo publish` artefacts, not instruction-file content. Panic-index and unsafe-index are parallel artefacts, not a renaming — no compat-shim concern.

### Test-Design notes

- No Rust `#[cfg(test)]` module is added or modified by this task.
- The "test plan" IS the AC verification matrix; review-findings and self-review re-run every AC command per the mandatory AC-verification-grep re-run rule (both agents' Checklist § 0).
- Initial-population entries (AC2) must be human-readable enough that a future hardening pass can act on "Preferred fix" without re-reading the source. Substantive content for each field is the only test; "is this placeholder?" is the only fail criterion.
- For the `window_registry.rs:160` entry specifically, the implementation phase MUST cross-check the entry text against the in-source `# Safety invariants` doc block (`window_registry.rs:66–84` — H3 at 66, numbered invariants 68–80, intra-doc-links 82–83) AND the inline `// SAFETY:` comment (lines 155–159) before commit. The entry's **Safety invariant** field is phrased as a cross-reference to those two locations (per subtask 1's mandate), so the three sources stay aligned by construction — drift between any two is still a `major` finding in review-findings, but the cross-reference structure makes drift in the entry itself a textual-mismatch check (does the entry name the canonical line ranges?) rather than a four-invariant content audit.
