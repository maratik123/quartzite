# Tickless eventloop

**Source:** issue #561
**Date:** 2026-05-24
**Tracked in:** #561

## Scope

1. Replace the hard-coded 1 ms `recv_timeout` in `quartzite-runtime::EventLoop::run` with a configurable tick policy expressed as `Option<Duration>`:
   - `None` → **tickless** (use `Receiver::recv()` — block until a message arrives or the channel is disconnected).
   - `Some(d)` → tick-based (use `Receiver::recv_timeout(d)` — current behaviour with caller-controlled tick duration instead of the hard-coded 1 ms).
2. Make tickless the **default** for both `EventLoop` and `Application`:
   - `EventLoop::new()` → tickless (`Option<Duration>` field set to `None`).
   - `Application::builder().build()` → tickless unless explicitly overridden.
3. Expose a configurable tick on `EventLoop` via a direct constructor (`EventLoop::with_tick(Option<Duration>) -> Self` — name design's call; Round 2 resolved direct-ctor over `EventLoopBuilder`). `EventLoop::new()` remains as a tickless convenience that delegates to `with_tick(None)`.
4. Add `Application::builder() -> ApplicationBuilder` (new type in `quartzite-runtime`), parallel to the existing `WindowedApplicationBuilder` in `quartzite-renderer`. Builder exposes a `tick_duration(Option<Duration>)` setter (or equivalent — exact method name design's call) and a `build() -> Result<Application, ApplicationError>` finaliser.
5. Extend `WindowedApplicationBuilder` (`quartzite-renderer`) with a `tick_duration(Option<Duration>)` setter that forwards into the inner `ApplicationBuilder` configuration before the runtime `Application` is constructed in `build()`.
6. Update `EventLoop::spawn` to accept the same `Option<Duration>` configuration so spawned worker loops inherit the same policy choice (default tickless).
7. All in-tree call sites of `Application::new()` (46 hits) migrated to `Application::builder().build()`. `Application::new()` is **retained** as a tickless-default convenience shorthand (added back post-review to reduce boilerplate — see Key decisions row "API shape on `Application`").
8. Update all in-tree call sites (`Application::new` ×46 hits, `EventLoop::new` ×27 hits across runtime + renderer + tests + examples) to the new API, defaulting to the tickless path unless the existing code's behaviour materially depends on the 1 ms wake-up (none currently do — see § Technical constraints).
9. Adjust `event_loop.rs` doctests + module-level doc to describe the tickless-by-default behaviour.
10. **Object-ify `EventLoop` and `Application`** (Round 5 Q1 resolved option (b) — full Object-ification via the macro path). Both types become `Object`s with `#[derive(Extend, Object)]` + `#[object_impl]`. Annotate `EventLoop::stop` and `Application::quit` with `#[slot]` so they are callable via `Object::invoke_method("stop", &[])` / `invoke_method("quit", &[])` and reachable from reflection-based `connect_signal_to_signal` wiring. Concretely:
    - **`EventLoop`**: add an `ObjectBase` field (`base: ObjectBase`) plus `#[derive(Extend, Object)] #[root]` on the struct. Wrap the existing inherent `impl EventLoop` with `#[object_impl]`. Annotate `stop` with `#[slot]`. `EventLoop::stop` must take `&mut self` to satisfy the macro-generated `invoke_method(&mut self, ...)` dispatcher (see § Technical constraints — slot receiver discipline).
    - **`Application`**: the singleton newtype `Application(Arc<ApplicationInner>)` cannot derive `Object` directly (the macro requires the `ObjectBase` field on the struct itself, and `Application` is a `Clone`-able handle, not the underlying state). Two implementation paths are admissible — design picks:
      - **(b1) Move `ObjectBase` into `ApplicationInner`** and emit a hand-rolled `AsObject` + `Object` impl on `Application` that forwards to `self.0.base` (and `self.0.base_mut` via `Arc::get_mut` / interior mutability — `Application` holds an `Arc`, so mutable access must round-trip through a `Mutex`/equivalent guarding the `ObjectBase`). Slot methods then take `&mut self` and rely on the same forwarding shape. The hand-rolled `Object` impl follows the precedent already established in `quartzite-core/src/connect.rs` (`Sender` / `Receiver` / `NullRecv` / `BoolRecv` tests — `:400-494`, `:496-589`, `:631-700`, `:706-769`).
      - **(b2) Extend the `#[derive(Object)]` macro** to accept an `#[object(arc_inner)]` (name design's call) attribute on a struct whose single field is `Arc<Inner>` and whose `Inner` carries the `ObjectBase`. The macro forwards every `AsObject` / `Object` method through the `Arc` (using interior mutability for the `&mut` paths). Larger scope but eliminates boilerplate for any future `Arc<Inner>` singleton.
    - Concrete decision between **b1** and **b2**: defer to design phase. **b1** is the conservative path (zero macro changes, follows an existing hand-rolled precedent); **b2** is the strategic path (macro grows once, future singleton/`Arc`-wrapped Objects ride free). Both satisfy the same ACs.

## Out of scope

1. **Adaptive / hybrid tick strategies** (e.g. busy-loop briefly then sleep, exponential back-off, idle detection). The user's `Option<Duration>` proposal covers two static modes; anything more sophisticated is a separate task.
2. **Renaming `EventLoop` / `Application` / `WindowedApplicationBuilder`.** API surface keeps current names; only constructor signatures change.
3. **Per-call tick override** (changing tick after `run()` has started). The tick is fixed at loop construction time; no runtime mutation.
4. **Multi-tick / hierarchical tick** (e.g. fast main tick + slow background tick). Single tick per loop.
5. **Timer-driver refactor.** Existing `ThreadDriver` / `AppDriver` / `PoolDriver` continue to fire on their own sleep mechanism (`park_timeout` / `condvar::wait_for`); whenever a tick is posted to the loop (directly by `AppDriver`, or transitively by the user's `connect_tick_queued`/`connect_tick_auto` callback for `ThreadDriver`/`PoolDriver`), the channel `send` wakes the loop's `recv()` / `recv_timeout(d)` regardless of tick mode. See § Technical constraints "Timer-driver wake-up in both modes" for the per-driver mechanic.
6. **winit `EventLoop` tick configuration.** `WindowedApplication` drives the OS event loop via winit; winit's wake-up policy is unchanged. The new tick policy applies only to the quartzite-runtime `EventLoop` that the `WindowedApplicationBuilder` constructs internally for the `quartzite_runtime::Application` singleton.
7. **Sub-millisecond timer accuracy guarantees.** Tickless mode wakes on channel activity; timer accuracy is bounded by the timer driver's own sleep mechanism (`park_timeout` / `condvar::wait_for`), not by the event-loop tick. This is a property of the existing driver design, not a regression introduced here.
8. **Adding `EventLoop` / `Application` to `ObjectTree`.** Even though they become `Object`s, they are not registered in any `ObjectTree`. They have no parent, no children, and `ObjectTreeExt::parent` / `::children` return `None` / empty. Rationale: `Application` is the *owner* of the tree (`ApplicationInner::object_tree`); making it a member would be circular. `EventLoop` lives inside `Application`. Tree-membership for runtime infrastructure objects can be a separate proposal if a use case surfaces. Their `ObjectId` is still globally unique (issued by `ObjectId::new`) and they remain discoverable via direct singleton access (`Application::global`) or thread-local registry (`LoopRegistry::get`).
9. **Renaming `#[slot]` / extending its semantics.** The annotation keeps its current meaning (`return type must be ()`, callable via `invoke_method`). Slot return values, async slots, generic slots, etc. — separate proposals.
10. **`Default` / construction-via-factory for `EventLoop` as an `Object`.** `EventLoop::default()` stays direct construction (tickless `Self::new()`); the factory-based `ObjectFactory::create("EventLoop", ...)` path is not exposed (constructing an `EventLoop` requires a thread context that the factory cannot supply meaningfully). Same applies to `Application` — `Application::builder().build()` is the sole entry point, not factory-based construction.

## Key decisions

| Question | Decision |
|---|---|
| API shape on `EventLoop` | Direct constructor `EventLoop::with_tick(Option<Duration>) -> Self` (final name design's call). Round 2 Q1 resolved: direct ctor over `EventLoopBuilder` — no parallel builder type for `EventLoop`. `EventLoop::new()` stays as a tickless-default convenience delegating to `with_tick(None)`. Constructor stays `const fn` where possible. |
| API shape on `Application` | New `ApplicationBuilder` in `quartzite-runtime`, obtainable via `Application::builder()`, exposing `tick_duration(Option<Duration>)` and `build() -> Result<Application, ApplicationError>`. `Application::new()` is **retained** as a tickless-default shorthand for `builder().build()` (restored post-review to reduce boilerplate). |
| API shape on `WindowedApplicationBuilder` | Add `tick_duration(Option<Duration>) -> Self` method (chained, `const fn` where possible — same shape as the existing `quit_on_last_window_closed`). `build()` passes the configured tick into the inner runtime `ApplicationBuilder` before calling its `build()`. |
| Default tick | `None` (tickless) for both `EventLoop::new()` and `Application::builder().build()`. The user explicitly requested tickless by default. |
| `EventLoop::spawn` signature | Replace `spawn(f)` with `spawn(tick: Option<Duration>, f)`. Tickless callers pass `None` explicitly — cheaper for readers than a second `spawn_with_tick` overload, and aligns with `EventLoop::with_tick` taking the same parameter. |
| `quit` processing | Leave as-is. Today's mechanism (works identically in both tickless and tick-based modes): `EventLoop::stop()` performs two actions: (1) sets `stop_requested: AtomicBool` to `true`; (2) `self.sender.send(Box::new(\|\| {}))` — pushes a no-op closure through the same mpsc the event loop drains. The no-op closure is the wake-up. In tickless mode `run()` blocks on `Receiver::recv()`; the no-op arrival returns `Ok(noop)`, `run()` executes the no-op (it does nothing), the outer `while !self.stop_requested.load(...)` re-checks the flag at the top of the next iteration, finds `true`, and exits. The post-loop `while let Ok(f) = receiver.try_recv()` drain then runs every remaining queued closure synchronously on the loop thread. Net effect: tickless and tick-based behave identically on `stop()` — wake within a single channel `send` latency, drain to completion before `run()` returns. No code change needed in either branch beyond the `recv()` vs `recv_timeout(d)` dispatch in `run()`. |
| Handling of `Some(Duration::ZERO)` | Design subagent's call. Two defensible options: (a) reject via `Result` in the builder's `build()` step (library safety idiom: non-panicking); (b) normalise silently to `None` (degenerate input → sensible behaviour). No correctness consequence either way; design picks. |
| `Default` impl on `EventLoop` | Keep — `EventLoop::default()` delegates to `EventLoop::new()` (tickless), preserving the existing trait. |
| `Default` impl on `EventLoop`'s tick field internals | Tick policy stored as `Option<Duration>` on the struct. No new types introduced (no `TickPolicy` enum, no `TickMode` wrapper — design subagent may revisit if `Some(ZERO)` handling motivates a richer type). |
| `Application::new()` deletion vs retention | **Retain as shorthand.** All 46 in-tree call sites migrated to `Application::builder().build()`; `Application::new()` kept as a one-line `#[inline]` delegate to `builder().build()` to reduce boilerplate (post-review decision). |
| Migration of in-tree call sites | Single PR; mechanical sweep using `ast-index usages` + targeted `Read`s for each site. No call site currently depends on the 1 ms wake-up being prompt — the tick was a polling artefact of the channel-based mpsc, not a published behaviour. |
| Effect on timer drivers | None. All three drivers fire on their own sleep mechanism; loop wake-up is via the channel `send` (direct in `AppDriver`, transitive via the user callback for `ThreadDriver` / `PoolDriver` when `connect_tick_queued`/`connect_tick_auto` is used). Channel sends wake `recv()` (tickless) and `recv_timeout(d)` (tick-based) identically — the tick value never gates timer delivery. See § Technical constraints "Timer-driver wake-up in both modes" for the per-driver mechanic + the worked example (`tick=50ms`, `interval=10ms` → ~10ms delivery cadence, not 50ms). |
| Constant `TICK_MS` in `event_loop.rs` | Remove. With `Option<Duration>` parameterising the loop, the hard-coded 1 ms is gone. |
| **Object-ification path (Round 5 Q1)** | **Option (b): in-scope this PR, full Object-ification via `#[derive(Extend, Object)] + #[object_impl] + #[slot]`.** Bundles tickless + Object-ification in one PR; closure-capture pattern remains available alongside the new reflection-based path. |
| **`EventLoop` Object shape** | `#[derive(Extend, Object)] #[root]` directly on `EventLoop`. Add `base: ObjectBase` field. The existing inherent `impl EventLoop` becomes `#[object_impl] impl EventLoop`. `stop` is annotated `#[slot]` and takes `&mut self` (was `&self`). Other inherent methods stay on the impl block (re-emitted untouched by `#[object_impl]`). The `EventLoop::run` method continues to take `&self` (does not need slot annotation; it is the loop driver, not a slot target). |
| **`EventLoop::stop` receiver change** | `&self` → `&mut self`. Forced by the macro: `Object::invoke_method(&mut self, ...)` is the dispatch entry, and the macro-generated arm calls `self.stop(...)` with the same `&mut` borrow. Call sites already hold `Arc<EventLoop>` / `&EventLoop` (44 hits per Round 5 inspection of `Application::quit` etc.); any caller needing `&mut` access goes through `Arc::get_mut` (single-owner case) or the slot-invocation path (`obj.invoke_method("stop", &[])`). Direct `.stop()` callers (the rare ones with `&mut EventLoop`) update trivially. **Trade-off accepted**: the receiver change is the smallest viable disruption — the alternative (interior mutability inside `EventLoop` for the `running` / `stop_requested` flags only, leaving `stop(&self)` intact) is already in place (`AtomicBool`), so the receiver change is purely a macro-API shape requirement, not a behavioural change. |
| **`Application` Object shape (b1 vs b2)** | Design picks. **b1** (hand-rolled `AsObject` + `Object` impl on `Application`, `ObjectBase` moved into `ApplicationInner`): conservative, zero macro changes, follows the `Sender` / `Receiver` precedent in `quartzite-core/src/connect.rs`. **b2** (macro extension `#[object(arc_inner)]` or similar): strategic, macro grows once, future `Arc<Inner>` singletons ride free. AC8 / AC9 are satisfied either way. Design phase chooses based on diff size and future-singleton likelihood. |
| **`Application::quit` receiver change** | `&self` → `&mut self`. Same macro-dispatch constraint as `EventLoop::stop`. `Application` is `Clone`-cheap (newtype around `Arc<ApplicationInner>`) so call sites that need `&mut` can clone and re-borrow if necessary. The `Drop` impl on `Application` is unaffected (still `&mut self` by trait contract). |
| **`ObjectId` for `Application` singleton** | A fresh `ObjectId` allocated at `ApplicationBuilder::build()` time (delegated to `ObjectBase::new()`'s default allocation via the `ObjectId::new()` counter). Singleton-ness is enforced by the `OnceLock<Arc<ApplicationInner>>` (`APP`), not by any property of `ObjectId`. Two consequences: (1) re-installation after process restart yields a different `ObjectId` — fine, IDs are not persistent; (2) tests that `Application::new` repeatedly in-process today already fail with `AlreadyExists` — Object-ification does not change that. |
| **`ObjectId` for `EventLoop`** | A fresh `ObjectId` per `EventLoop::new()` / `EventLoop::with_tick(...)` call. `EventLoop::spawn` allocates an `ObjectId` for the spawned-thread loop. The main-thread loop owned by `Application` has its `ObjectId` allocated by `ApplicationBuilder::build()`. No coupling between `EventLoop` and `Application` `ObjectId`s. |
| **`ObjectBase::thread_id` for `EventLoop`** | Captured at `EventLoop::new()` / `with_tick()` time — the **constructor thread**, not the loop-runner thread. This matches `ObjectBase`'s existing semantics (`thread_id = std::thread::current().id()` in `ObjectBase::new`). Documentation note required: the `thread_id` on `EventLoop`'s base is the thread that *constructed* the loop, which may differ from the thread that calls `run()`. For `Application`, the constructor thread is also the main thread (per `main_thread_id` field), so they agree. For `EventLoop::spawn`, the constructor thread is the spawning thread (the parent), not the spawned worker thread — `ObjectBase::thread_id` does not track the worker. **Decision**: this asymmetry is accepted; the `Application::main_thread_id()` accessor remains the authoritative source for the loop-runner thread, and `EventLoop` callers wanting the runner thread use `is_running()` + `install_for_current_thread()`'s `ThreadId` capture (preserved). Per-thread queued-signal routing keeps using `LoopRegistry` (keyed by the runner thread's `ThreadId`), unchanged. |
| **Tree membership** | Neither `Application` nor `EventLoop` is registered in any `ObjectTree`. `Application` *owns* the tree; making it a member is circular. `EventLoop` lives inside `Application`. `ObjectTreeExt::parent` / `::children` return `None` / empty when called on either. Reflection-based wiring via `invoke_method` / `connect_signal` works regardless of tree membership (the meta-system does not require tree presence — `Sender` / `Receiver` / `NullRecv` in `connect.rs` are also tree-less Objects). |
| **`MetaObject` class names** | `"EventLoop"` and `"Application"` (the existing identifier names). Class-name registration is done at first-call to `meta_object()` via the macro-generated `__meta_init_<Type>` initialiser (same as `Timer` and every other Object-derived type). |
| **Slot semantics on `stop` / `quit`** | Both `#[slot]` annotated, both take `&mut self`, both return `()`. The macro's `invoke_method` arm dispatches `obj.invoke_method("stop", &[])` to a no-arg, `()`-returning slot call. The closure-capture pattern (`signal.connect(\|_\| app.quit())`) continues to work alongside. |

## Technical constraints

- **Crate boundaries.** `EventLoop` + new `ApplicationBuilder` live in `quartzite-runtime`. `WindowedApplicationBuilder` lives in `quartzite-renderer` and depends on `quartzite-runtime` (already). No new cross-crate edges required.
- **Object macro dependency edge.** `quartzite-runtime` already depends on `quartzite-core` (where `ObjectBase` / `AsObject` / `Object` / `MetaObject` live) and on `quartzite-macros` (where `#[derive(Extend, Object)]` + `#[object_impl]` live) — `Timer` already uses `#[derive(Extend, Object)]` in `quartzite-runtime/src/timer.rs:163`. No new dependency edges required for Object-ification.
- **`no_std` / `libm` build path.** `quartzite-runtime` requires `std` (uses `std::thread`, `std::sync::mpsc`, `std::time::Duration`); already gated by feature flags in the workspace. No change. `ObjectBase` already supports both `std` and `no_std` paths.
- **`Duration::ZERO` semantics.** `Receiver::recv_timeout(Duration::ZERO)` returns immediately with `Err(RecvTimeoutError::Timeout)` when no message is queued — i.e. a degenerate busy-loop. The builder must either reject this input or normalise it (see Key Decisions row 6). Design subagent picks the precise mechanism.
- **Channel-disconnect handling.** Existing `match` arm `Err(mpsc::RecvTimeoutError::Disconnected) => break` becomes `Err(mpsc::RecvError) => break` in the tickless branch (`recv()` returns `RecvError`, not `RecvTimeoutError::Disconnected`). Two error types must be handled in the tickless vs tick-based code paths; design picks the dispatch shape (e.g. inner `match` per branch, or wrapping in a small helper that normalises to a unified `LoopExitReason`).
- **`stop()` wake-up.** Already implemented correctly. `stop()` does two things: (1) `stop_requested.store(true, SeqCst)`; (2) `sender.send(Box::new(\|\| {}))` — pushes a no-op closure. In tickless mode `run()` is blocked on `Receiver::recv()`; the no-op arrival unblocks it, the no-op executes (does nothing), the outer `while !stop_requested.load(SeqCst)` re-checks the flag, sees `true`, exits. Then the post-loop `try_recv()` drain runs every remaining queued closure synchronously. Both modes — tickless and tick-based — observe identical exit semantics (single-channel-send wake latency + full drain before return). No code change required for this in either mode.
- **Drain-on-exit invariant.** The post-loop `while let Ok(f) = receiver.try_recv()` drain stays — applies to both modes.
- **Slot receiver discipline (Object macro requirement).** The `#[object_impl]` macro generates `Object::invoke_method(&mut self, name, args)`, and its match-arm dispatch calls `this.<method>(...)` where `this: &mut Self`. Any method annotated `#[slot]` MUST take `&mut self` (not `&self`). This forces:
  - `EventLoop::stop(&self)` → `EventLoop::stop(&mut self)`
  - `Application::quit(&self)` → `Application::quit(&mut self)`
  Internally both implementations remain unchanged (atomic stores + channel sends do not need `&mut self`); the receiver type is a macro-shape requirement, not a synchronisation requirement.
- **`Object` requires `Send`.** `pub trait Object: AsObject + Send` (`quartzite-core/src/traits.rs:94`). `EventLoop` is already `Send` (channel + atomics + parking_lot). `Application` (newtype around `Arc<ApplicationInner>`) is `Send` provided `ApplicationInner: Send + Sync` — already the case (Mutex + Arc fields). No new bounds required.
- **`#[derive(Object)]` macro restrictions.**
  - Only supports structs with named fields (`quartzite-macros/src/object/parse.rs:43-58`).
  - Rejects generic structs (`quartzite-macros/src/object/parse.rs:61-66`).
  - **Implications**:
    - `EventLoop` is a named-field non-generic struct → derives directly with an added `base: ObjectBase` field.
    - `Application(Arc<ApplicationInner>)` is a **tuple struct** → cannot derive `Object` directly. Hence the b1 / b2 split in Key Decisions row "**Application Object shape**".
- **Hand-rolled `Object` impl precedent (path b1).** `quartzite-core/src/connect.rs` already carries hand-rolled `AsObject` + `Object` impls for `Sender` (`:400-494`), `Receiver` (`:496-589`), `NullRecv` (`:631-700`), and `BoolRecv` (`:706-769`). All four follow the same shape: static `MetaObject`, no props, hand-written `connect_signal` / `emit_signal` arms. The `Application` hand-rolled impl would mirror this pattern, with one extension: `object_base(&self) -> &ObjectBase` forwards to `&self.0.base` (via the `Arc<ApplicationInner>`), and `object_base_mut` is the awkward case (`Arc` is read-only) — see Key Decisions row "**Application Object shape**" for the resolution (e.g. wrap `ObjectBase` in an interior-mutability cell, or only support `object_base` and reject `object_base_mut` callers with a `panic!` documented as "not applicable to singleton Object"). Design picks.
- **Macro extension scope (path b2).** If b2 is chosen, the macro extension adds one of:
  - **(b2-i) `#[object(arc_inner)]` attribute** on the outer struct, plus a `#[base]` marker on the `Inner` struct's `ObjectBase` field. The macro generates `AsObject` for the outer that forwards via `Arc::deref()`. `object_base_mut` requires interior mutability on `Inner` (e.g. `RwLock<ObjectBase>` or split out the `name` field into its own `Mutex`).
  - **(b2-ii) `#[derive(Object)]` on the `Inner` struct directly** + a separate `#[derive(Extend)]` on the outer tuple struct that knows about the `Arc` indirection. Cleaner — `Inner` is just a normal Object, the outer is "an Object handle". Either variant is design's call.
- **Linter posture.** New `#[must_use]` on `ApplicationBuilder` (mirrors `WindowedApplicationBuilder`). New doc strings on every public item per workspace `missing_docs = "deny"`. `cargo clippy --workspace --all-targets -- -D warnings` MUST pass.
- **Documentation.** Every new public fn / type / method carries `///` doc with `# Examples` for new public items per workspace `missing_docs = "deny"` + `ai-docs/doc-convention.md` (single-line items get `# Examples`; new types get a top-level doc paragraph). Object-ification adds `ObjectBase` to the public field list of `EventLoop`; that field carries its own `///` doc per the same convention.
- **`_Simple._` markers / `#[inline]`.** Per AGENTS.md § Code Style → `#[inline]` rule: simple (no branches/loops, ≤ 1 non-simple call) concrete fns / inherent methods MUST carry `#[inline]`. `ApplicationBuilder::tick_duration` and `WindowedApplicationBuilder::tick_duration` contain a `match` expression (branching) — they do NOT carry `#[inline]`. `Default::default()` and similar truly-simple one-liners do carry `#[inline]`.
- **No `unsafe`.** Channel + atomics + parking_lot only. Object-ification does not introduce `unsafe` — the existing macro pattern is `safe`.
- **Tracing.** Existing `debug_span!`/`trace_span!` spans in `event_loop.rs` stay. No new spans required; tick-mode selection is loop construction time, not per-iteration. The slot-invocation path (`invoke_method`) does not require new spans either — `stop` / `quit` already carry their own `debug_span!`.
- **Timer-driver wake-up in both modes (Round 7 Q1).** Verified mechanically by inspecting `quartzite-runtime/src/timer_drivers.rs` + `event_loop.rs:run`. Three driver shapes, all compatible with tickless and tick-based loops because the loop's `Receiver::recv()` / `Receiver::recv_timeout(d)` both wake on **any** channel `send`, not on the tick boundary:
  - **`AppDriver`** (`timer_drivers.rs:169-210`): each fire calls `Application::global().post_event(Box::new(move || cb_clone()))`. `post_event` forwards to the main `EventLoop::sender`. The channel send wakes the loop's `recv()` (tickless) / `recv_timeout(d)` (tick-based) **immediately** — no lag to the next tick. A tick-based loop with `tick = 50ms` and a timer with `interval = 10ms` still observes a fire every ~10ms, not every 50ms — the channel send breaks `recv_timeout` early.
  - **`ThreadDriver`** (`timer_drivers.rs:78-114`): `park_timeout(interval)` → `callback()` invoked **on the driver thread**, not the loop thread. Whether the loop sees the fire depends on what the callback does: `connect_tick` (Direct) runs the slot on the driver thread (no loop wake-up needed; intentional); `connect_tick_queued` / `connect_tick_auto` (cross-thread → Queued) posts the slot to the receiver's `EventLoop` via the channel, which wakes the loop the same way `AppDriver` does. The loop's tick mode is irrelevant to this dispatch.
  - **`PoolDriver`** (`timer_drivers.rs:373-403`): `condvar.wait_for(deadline)` → callback invoked on the pool thread. Same as `ThreadDriver`: loop wake-up happens iff the callback is queued/posted (the normal usage via `connect_tick_queued`); Direct delivery skips the loop intentionally.
  Net effect: timer delivery latency in **either** loop mode is `driver_sleep_jitter + channel_send_latency`. The loop's tick value does not gate timer delivery; it only governs how often `recv_timeout` returns spuriously when the channel is idle (tickless = never; tick-based = every `d`). No code change required in any driver.
- **Singleton-as-Object semantics summary.**
  - **`ObjectId`**: globally unique, allocated by `ObjectId::new()` counter (existing). One ID per `Application` install per process; one ID per `EventLoop::new()` call.
  - **Tree membership**: none (see § Out of scope item 8). `Application::object_tree()` returns the tree but `Application` is not *inside* the tree.
  - **Thread affinity (`ObjectBase::thread_id`)**: captured at constructor-thread time (see Key Decisions row "**`ObjectBase::thread_id` for `EventLoop`**"). For `EventLoop` constructed by `Application::builder().build()`, this matches `Application::main_thread_id()`. For `EventLoop::spawn`, it captures the spawning thread, not the worker thread — `LoopRegistry` remains authoritative for queued-signal routing.
  - **Global accessibility**: `Application::global()` (existing) returns `Option<Application>` — the `Object`-aware handle. From any `Object` reference, `meta_object().class_name == "Application"` identifies the singleton; reflection-based wiring (`connect_signal_to_signal`) accepts the same `&mut dyn Object` handle.

## Open questions

- **Final identifier name for the direct tick constructor on `EventLoop`** (`with_tick(Option<Duration>)` vs `with_tick_duration(Option<Duration>)` vs re-signing `new(Option<Duration>)` and dropping the convenience). Round 2 Q1 fixed the shape (direct ctor); the exact name is design's call.
- **Builder method name** on `ApplicationBuilder` / `WindowedApplicationBuilder` (`tick_duration` vs `tick` vs `with_tick_duration`). Design picks.
- **`Some(Duration::ZERO)` handling**: reject via `Result` at `build()` time vs normalise silently to `None`. Both defensible — see Key Decisions row "Handling of `Some(Duration::ZERO)`" + AC9 sub-item (e). Design picks; AC9 is satisfied either way.
- **Whether the runtime `ApplicationBuilder` lives in its own file** (`quartzite-runtime/src/application_builder.rs`, mirroring `quartzite-renderer/src/application_builder.rs`) or inline in `application.rs`. File-size rule (AGENTS.md § File size: soft target 200–400 lines) likely favours a sibling file; design picks per the live `application.rs` line count after the diff lands.
- **Path b1 vs b2 for `Application` Object-ification**: hand-rolled `AsObject` + `Object` impls on `Application` (b1) vs macro extension `#[object(arc_inner)]` or equivalent (b2). Design picks. Two scenarios drive the choice:
  - **b1 picked** → keep `ApplicationInner` as the `ObjectBase` carrier; hand-roll `AsObject` + `Object` on `Application` following the `Sender` / `Receiver` precedent. Defer the macro extension via § Deferred row.
  - **b2 picked** → extend `quartzite-macros/src/object/parse.rs` + `codegen.rs` to support the chosen attribute shape; `Application` derives the macro, `ApplicationInner` carries the `ObjectBase`. Macro change unblocks any future `Arc<Inner>` singleton Object.
- **`Application::object_base_mut` semantics under b1**: if the b1 path is chosen, `Application` holds `Arc<ApplicationInner>` (shared, not mutable). `object_base_mut(&mut self) -> &mut ObjectBase` cannot return a real mutable reference because `Arc::get_mut` requires exclusive ownership of the `Arc`. Three sub-options (design picks):
  - (i) wrap `ObjectBase` in `parking_lot::Mutex` on `ApplicationInner` and return a guard-derived `&mut` (lifetime gymnastics needed — `Object` trait's `object_base_mut` signature is `fn(&mut self) -> &mut ObjectBase`, a guard cannot satisfy that).
  - (ii) panic in `object_base_mut` with a clear message: "Application singleton's ObjectBase cannot be mutated through the shared handle; use ObjectTree::rename for name changes". This is a documented limitation, not a silent failure.
  - (iii) split `ObjectBase` into `&Arc<ObjectBase>` (read-only fields) + per-field interior mutability for `name` / `signals_blocked`. Largest refactor, cleanest semantics.
  Design picks; the choice is internal to b1.
- **`#[slot]` on other inherent methods (`exec`, `post_event`, `is_running`, etc.)**: scope decision. Only `stop` / `quit` are annotated per Round 4's explicit request. Adding others is a future Object-ification refinement; see § Deferred row "Reflection-based set_property knobs on Application".
- **`object_part!` accumulation for multi-block impls**: `EventLoop`'s inherent impl currently has ~10 methods. The `#[object_impl]` attribute can be placed on the single inherent impl block, or split via `#[object_part]` (for accumulating) + `#[object_impl]` (terminator). Design picks based on file-size / readability.
