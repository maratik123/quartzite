# LineEdit caret + selection rendering

**Source:** issue #405
**Date:** 2026-05-24
**Tracked in:** #405

> Surfaced from [`ai-docs/deferred/widget-backlog.md`](../deferred/widget-backlog.md). Source spec: [`2026-05-15-container-lineedit-rendering.spec.md`](done/2026-05-15-container-lineedit-rendering.spec.md). Blocker #539 is closed (visual contract landed in PR #552); the TextEdit-side mechanism PR (#317 / branch `feat/2026-05-23-textedit-caret-selection`) extracted every reusable seam (`StyleClock`, `Style::caret_visible_now` / `prefers_reduced_motion`, `Painter::text_carets` / `text_visual_lines`, `DefaultStyle::start_blink_timer`) — this spec wires those seams into `LineEdit` per [`design-system/proposals/caret-and-selection.md`](../../design-system/proposals/caret-and-selection.md) without adding any new public seam.

## Scope

Wire a selection model + caret rendering onto `LineEdit` and paint them via `DefaultStyle::paint(&LineEdit, …)`, reusing every seam introduced by the TextEdit PR (#317):

- **Selection-model state on `LineEdit`** — two new `#[prop]` fields on the struct (matching the design-proposal *Diff sketch* and the `TextEdit` shape verbatim):
  - `pub caret: usize` — byte index into `text` (0..=`text.len()`), defaults to `0`.
  - `pub selection_anchor: Option<usize>` — byte index, `None` ⇒ no selection. When `Some`, the selection range is `min(anchor, caret)..max(anchor, caret)`.
  - One inherent helper `pub fn selection_range(&self) -> Option<(usize, usize)>` returning the normalised `(start, end)` byte indices when a selection exists (returns `None` when `selection_anchor.is_none()` *or* `anchor == caret` — zero-length collapsed selection is caret-only, matching `TextEdit`).
  - Property-setter `set_caret(usize)` / `set_selection_anchor(Option<usize>)` `#[slot]` slots that clamp `n` to `0..=text.len()`, no-op when value unchanged, no-op when `read_only`, and emit one new `Signal` `selection_changed: Signal<()>` only when the resolved `(caret, selection_anchor)` state actually changes. Mirrors the `TextEdit` slots in shape and the `set_text` precedent in the same file (no-op on unchanged value, no-op on `read_only`).
- **Caret painting** in `impl Paint<LineEdit> for DefaultStyle`, per design-proposal §§ 1–3, 6, 7, plus the LineEdit-specific § 2 *vertical centring*:
  - Caret rect = `Rect::new(Point::new(caret_x, caret_y), Size::new(1, line_height))` where `caret_y = geom.top() + (geom.height() - line_height) / 2` (design-proposal § 2: *Vertically centered within the rect for `LineEdit`*). Filled with the state-resolved text brush.
  - Caret painted only when `is_focused() && !read_only && is_enabled() && self.caret_visible_now()`. The `Style::caret_visible_now` method was shipped by #317 and is consumed unchanged — no new seam.
  - Caret-X is read from `Painter::text_carets(&w.text, &font)` (shipped by #317): the painter calls `cursor.advance_to(w.caret)` then reads `cursor.caret_x()`. `cursor.line_top()` / `cursor.line_height()` give the font-level metrics used to centre the caret vertically inside `geom`.
  - Empty-text caret: design-proposal § 2 — left-aligned at the padding inset (i.e. `geom.left()`) when `w.text.is_empty()`; vertically centred. `Painter::text_carets("", &font)` returns a cursor whose `cluster_count == 0`; `cursor.advance_to(0)` followed by `cursor.caret_x()` MUST return the inset x (matches the existing `Painter::draw_text_in(geom, "", …)` behaviour — the live `parley`-backed cursor and every test/`Null`/`Recording` cursor in the workspace already produce a zero-length-text x at `geom.left()` by spec contract of #317). No special-case branch in the LineEdit paint code.
  - Caret-Y centring composes orthogonally with the placeholder ladder: when `w.text.is_empty() && !w.placeholder.is_empty()` the placeholder is drawn first (existing path), then the caret is painted on top at the padding inset — the caret remains visible above the placeholder glyphs because the placeholder is half-alpha (`disabled(text_color)`) and the caret is full-alpha state-resolved `Text`.
- **Selection painting** in the same impl, per design-proposal §§ 4, 7, 8, with the LineEdit-specific single-line simplification:
  - **Single rectangle only** — no wrap path. The selection rect is computed via `Painter::text_carets(&w.text, &font)`: call `cursor.advance_to(sel_start)` → read `sel_start_x = cursor.caret_x()`, then `cursor.advance_to(sel_end)` → read `sel_end_x = cursor.caret_x()`. The rect is `Rect::new(Point::new(sel_start_x, caret_y), Size::new(sel_end_x - sel_start_x, line_height))` (same vertical extent as the caret — design-proposal § 4: *Hugs the line-box height, not glyph metrics*). `Painter::text_visual_lines` is **not** called from the LineEdit paint path.
  - Selection fill = `palette.color(Highlight, ColorGroup::Normal)` when focused; `disabled(Highlight)` (α-halved) when unfocused-with-selection. Pressed-state interaction (see Key Decisions row "Selection vs. pressed-state colour ladder") is resolved by the documented default below.
  - Selected-glyph foreground = second text pass clipped via `Painter::save` + `clip_rect` + `draw_text_in` + `restore`, brush = `HighlightedText` (focused) or `Text` (unfocused-with-selection).
  - Disabled: neither caret nor selection painted; selection range preserved in state.
- **Read-only with selection** (design-proposal § 6): selection painted (copy semantics); caret hidden.
- **Snapshot tests** under `quartzite-style/tests/snapshots/shared/` (and dark variants), tracking the design-proposal *Snapshot tests* list verbatim plus one extra for read-only parity with TextEdit:
  - `line_edit_focused_empty.png` — empty `text`, caret visible at left padding inset.
  - `line_edit_focused_caret.png` — `"abc"` with caret between `b` and `c`.
  - `line_edit_focused_selection.png` — `"abc"` with `bc` selected.
  - `line_edit_unfocused_selection.png` — `"abc"` with `bc` selected, blur applied (α-halved Highlight + `Text` foreground).
  - `line_edit_read_only_selection.png` — `"abc"` read-only with `bc` selected: selection painted, caret hidden, read-only overlay still present (matches the existing `text_edit_read_only_selection.png` precedent — added here as parity coverage even though the design-proposal *Snapshot tests* list cites it under TextEdit only).
  - Dark-mode siblings (`dark_line_edit_focused_empty.png`, etc.) — one per light golden, matching the existing snapshot-suite convention.
- **Determinism**: tests construct `DefaultStyle::with_clock(StyleClock::pinned(true))` (shipped by #317) so `caret_visible_now → true` is deterministic — no wall-clock reads happen inside the snapshot path.
- **Tracking-issue comment**: post a comment on #317 (the TextEdit PR's tracking issue) noting that the LineEdit follow-up has landed, referencing this PR's number once it's open. No tracking comment on #405 is needed (this spec **is** #405).

## Out of scope

- **Input handling** — keystrokes, mouse-click positioning, arrow-key caret movement, drag-to-select, double-click word selection, triple-click line selection. No `winit`-side wiring lands here. The caret + selection update purely through the new public `set_caret` / `set_selection_anchor` slots; integration with a future input-handling pass is a follow-up (same boundary as the TextEdit spec).
- **Password masking / `echo_mode`** — `LineEdit` has no `echo_mode` / password field today. When password masking lands, the design proposal's open-question about whether the caret should expose the byte position of glyph clusters in masked input becomes live; out of scope here.
- **IME composition** — composition underline, candidate-window placement. Logged in design-proposal *Open questions / follow-ups*; not implemented for either widget yet.
- **Block-cursor (overwrite mode)** — `LineEdit` has no `overwrite_mode` field; the design proposal defers this.
- **Triple-click / double-click word-or-line selection** — input-handling concern.
- **Horizontal text scrolling inside `LineEdit`** (content overflow when `text` is longer than the visible rect) — the selection painter clips to `geometry()` (already implied by `draw_text_in`); a future scroll-aware spec covers horizontal viewport translation. Same boundary as the TextEdit spec (which deferred vertical scroll).
- **New seams of any kind** — `StyleClock`, the two `Style` trait methods, the two `Painter` cursor methods, and the `DefaultStyle::start_blink_timer` invalidation seam shipped in #317. This spec adds zero new public items outside the `LineEdit`-specific fields + slots + helper + signal. Touching any of those seams in this PR is out of scope.
- **`TextEdit`-side changes** — the TextEdit caret/selection path is shipped; not touched here.
- **Per-widget caret-blink phase deviation** — the design-proposal *follow-ups* item from #317's spec; not in scope.

## Deferred

- Password / masked input (`echo_mode`) on `LineEdit` | needs a `mode` enum field; caret position exposure on masked input is a design-proposal *Open question* | new issue when input handling lands
- IME composition underline | needs a `ColorRole` decision and shaping integration | shared with TextEdit's deferred; new issue when IME lands
- Block-cursor / overwrite mode | needs a `mode` field on `LineEdit`; same boundary as TextEdit | new issue when input handling lands
- Horizontal scroll-offset rendering on `LineEdit` (content overflow) | needs a horizontal viewport-offset model | new issue when input handling's scroll-policy lands
- Word / line selection on multi-click | input-handling concern | folded into the input-handling pass

## Key decisions

| Question | Decision |
|---|---|
| Visual contract source | [`design-system/proposals/caret-and-selection.md`](../../design-system/proposals/caret-and-selection.md). Every visual decision (caret width, blink cadence, selection-rect tiling, unfocused-with-selection greying, read-only / disabled rules, vertical-centring of the caret in single-line widgets) follows the proposal verbatim. This spec adds **no** new visual choices; it implements the proposal. |
| Reuse vs. re-introduce seams | **Reuse-only.** Every seam needed (`StyleClock`, `Style::caret_visible_now`, `Style::prefers_reduced_motion`, `Painter::text_carets`, `Painter::text_visual_lines`, `DefaultStyle::start_blink_timer`) shipped with #317. This spec adds **no** new public items outside the `LineEdit`-specific selection-model fields + signal + slots + helper. Touching the shared seams (signature change, default-impl change, new methods on the cursor traits, etc.) is out of scope; if the implementation discovers a needed seam adjustment, raise it via the AGENTS.md *Spec-Amendment recipe*. |
| Widget scope | **LineEdit only.** TextEdit caret/selection landed in #317; not touched here. |
| Selection-model storage | Two new `#[prop]` fields on `LineEdit`: `pub caret: usize` and `pub selection_anchor: Option<usize>`. Identical shape to `TextEdit::caret` / `TextEdit::selection_anchor` so the two widgets share a selection model (the single-line constraint is enforced by the widget's behaviour, not by the model — design-proposal *Diff sketch* and the issue comment on this issue confirm this is intentional). |
| Selection-range helper | `pub fn selection_range(&self) -> Option<(usize, usize)>` — inherent method, returns `Some((min(anchor, caret), max(anchor, caret)))` when `selection_anchor.is_some()` *and* `anchor != caret`; `None` otherwise. Single source of truth for both selection-paint passes. Same semantics as `TextEdit::selection_range`. |
| New signal | `pub selection_changed: Signal<()>` — emitted by `set_caret` / `set_selection_anchor` slots whenever the resolved selection-or-caret state changes. Carries no payload (consistent with framework default of "notify, then re-read"). Same shape as `TextEdit::selection_changed`. |
| Out-of-range caret / anchor | Both clamped to `0..=text.len()` on write via the setter slots. Out-of-range values from direct field mutation (Rust permits since fields are `pub`) are clamped at paint time as a defence in depth — paint never panics on bad indices. Same rule as `TextEdit`. |
| Byte vs. char-index for caret / anchor | **Byte** index into `text` (a `String`). Matches `String::char_indices()` callers and the proposal. Paint code translates via the painter cursor; invalid UTF-8 boundary indices are clamped to the nearest valid one by the cursor's `advance_to`. Same rule as `TextEdit`. |
| Caret vertical position | **Vertically centred inside `geom`** — design-proposal § 2 *"Vertically centered within the rect for LineEdit (single-line widget)"*. Computed as `caret_y = geom.top() + (geom.height() - line_height) / 2`. Distinct from the `TextEdit` rule (top-aligned at `line_top` returned by the cursor). The cursor's `line_top()` is **not used** for LineEdit; only `line_height()` plus the widget geometry determine `caret_y`. |
| Empty-text caret X | Left padding inset — `geom.left()`. `Painter::text_carets("", &font)` produces a cursor whose `advance_to(0)` + `caret_x()` returns `geom.left()` (contract pinned in the #317 cursor-trait rustdoc); no special-case branch is needed in the LineEdit paint code. |
| Selection-rect source | **`text_carets` only.** No `text_visual_lines` call. Selection start-x = `text_carets.advance_to(sel_start).caret_x()`; selection end-x = `text_carets.advance_to(sel_end).caret_x()`. Rect = `(sel_start_x, caret_y, sel_end_x - sel_start_x, line_height)`. The `text_visual_lines` cursor is unused in the LineEdit paint path; this matches the issue-comment plan ("No line-wrap path in `paint_selection` (single line only)"). |
| Selection vertical extent | Same as caret: line-box height (`line_height`), vertically centred inside `geom` — design-proposal § 4 *"Hugs the line-box height, not glyph metrics. Same height the caret uses"*. |
| Selected-glyph overdraw mechanism | `Painter::save() → Painter::clip_rect(sel_rect) → Painter::draw_text_in(geom, &w.text, &font, brush(HighlightedText or Text), Left) → Painter::restore()`. Same mechanism as TextEdit (no new `draw_text_clipped` API). |
| Unfocused-with-selection | Per design-proposal § 8: `disabled(Highlight)` selection fill + `Text` (not `HighlightedText`) glyph foreground. Re-uses the existing `disabled(c)` helper in `default_style/mod.rs`. Same rule as TextEdit. |
| Read-only with selection | Per design-proposal § 6: selection painted, caret hidden. Read-only overlay (`read_only_overlay` brush, existing) still applies on top of `Base` fill but *under* the selection fill — keeps copy-semantics legible while signalling non-editability. |
| Disabled | Per design-proposal § 7: neither caret nor selection painted; selection range preserved through enable cycles. |
| Reduced-motion fallback | Per design-proposal § 3: steady-on (no blink) when the host surfaces `prefers_reduced_motion = true`. The plumbing landed in #317 (`Style::prefers_reduced_motion`); consumed unchanged. |
| Selection vs. pressed-state colour ladder | **Selection layer wins, pressed text-brush still applies to non-selected text.** `LineEdit`'s existing pressed-state ladder inverts the base fill to `Highlight` and the text to `HighlightedText` (see `default_style/mod.rs:342-345`). When `pressed && selection_range().is_some()`, the design proposal does not specify this co-occurrence (selection display is normally driven by focus, not by transient mouse-down state). Default: paint selection *on top of* the pressed-inverted base fill, using the focused-with-selection brushes (Highlight × Normal fill + HighlightedText foreground inside the selection range); non-selected glyphs continue to use the pressed `HighlightedText` brush. The visual result is a uniform Highlight band across the selection range (selection-fill == pressed-fill colour, no visible boundary), with selected glyphs reading as `HighlightedText` either way. This is the natural extension of the focused-with-selection rule and is verified by a `RecordingPainter` unit test asserting the rect ordering + brush colour. No snapshot golden is added for pressed-with-selection (mouse-down state is transient). |
| Placeholder + caret co-occurrence | When `w.text.is_empty() && !w.placeholder.is_empty() && w.is_focused() && !w.read_only && w.is_enabled() && self.caret_visible_now()`, the caret is painted at `geom.left()` (empty-text X rule above) on top of the placeholder text. Selection cannot occur when text is empty (no byte range to anchor), so the placeholder + selection combination is moot. |
| File-size posture for `mod.rs` | Adding the LineEdit caret + selection paint to `quartzite-style/src/default_style/mod.rs` grows the file. The current `mod.rs` is ~432 lines (`wc -l` at the time of this spec). The TextEdit precedent extracted `Paint<TextEdit>` into a sibling `default_style/text_edit.rs` module when the file crossed the soft cap. This spec follows the same convention: **extract `Paint<LineEdit>` into a sibling `default_style/line_edit.rs` module** as part of the implementation, even if the post-growth `mod.rs` size would still be under 500 lines — the symmetry with `text_edit.rs` is the maintainability goal, not just the cap-avoidance. |
| Tracking-issue comment target | **Comment on #317**, not #405. #405 *is* this spec; commenting on it is self-referential. The TextEdit PR posted a tracking comment on #405 (this issue) for the follow-up; the LineEdit PR returns the favour by posting on #317 confirming the follow-up has landed and referencing this PR. Same convention as the TextEdit spec. |

## Acceptance Criteria

| # | Criterion |
|---|-----------|
| AC1 | `LineEdit` exposes public fields `caret: usize` and `selection_anchor: Option<usize>`, plus a `selection_changed: Signal<()>` signal and an inherent `selection_range(&self) -> Option<(usize, usize)>` method. Default value of both fields is `0` / `None` respectively on `LineEdit::new()` and `LineEdit::default()`. |
| AC2 | `set_caret(n)` clamps `n` to `0..=text.len()`, emits `selection_changed` only when the resolved `(caret, selection_anchor)` state actually changes, and is a no-op when `read_only`. `set_selection_anchor(opt)` follows the same pattern (clamp `Some(n)` to `0..=text.len()`, no-op when read-only, emit only on resolved-state change). |
| AC3 | `selection_range()` returns `Some((min(a, c), max(a, c)))` when `selection_anchor == Some(a)` and `caret == c` and `a != c`; returns `None` when `selection_anchor.is_none()`; returns `None` when `a == c` (zero-length selection is treated as caret-only). |
| AC4 | `DefaultStyle::paint(&LineEdit, …)` paints a 1 px-wide caret rect at `caret_x × caret_y..caret_y + line_height` filled with the state-resolved text brush *only when* `is_focused() && !read_only && is_enabled() && self.caret_visible_now()`, where `caret_y = geom.top() + (geom.height() - line_height) / 2`. A `RecordingPainter`-based unit test verifies the caret `fill_rect` is *absent* under `is_focused == false`, under `read_only == true`, under `is_enabled() == false`, and under `caret_visible_now == false` (pinned via `StyleClock::pinned(false)`); and *present* otherwise. |
| AC5 | `DefaultStyle::paint(&LineEdit, …)` with a selection (`text = "abc"`, `caret = 1`, `selection_anchor = Some(3)`) paints exactly one selection `fill_rect` whose horizontal span is `(sel_start_x, sel_end_x)` and whose vertical span is `line_height` (centred via the same `caret_y` formula). The selection `fill_rect` is emitted *after* the main `draw_text_in` (covering already-drawn normal-coloured glyphs in the selection region); a clipped `draw_text_in` overdraw then re-renders highlighted glyphs on top. A `RecordingPainter` unit test asserts the fill-rect presence, its span, and the rect ordering. |
| AC6 | `DefaultStyle::paint(&LineEdit, …)` never emits more than one selection `fill_rect` (single-line widget — `text_visual_lines` is **not** called from the LineEdit paint path; only `text_carets` is consulted). Unit test asserts `events.iter().filter(is_selection_fill).count() == 1` under any non-empty selection range. |
| AC7 | When `is_focused == false` *and* `selection_range().is_some()`, the selection `fill_rect` uses `disabled(palette.color(Highlight, Normal))` (α-halved) *and* the selected-glyph overdraw brush is `palette.color(Text, …)` rather than `HighlightedText`. Unit test verifies the captured brush colour matches the alpha-halved Highlight + `Text`-not-`HighlightedText` overdraw brush. |
| AC8 | When `is_enabled() == false`, *no* caret `fill_rect` is emitted *and* *no* selection `fill_rect` is emitted. The selection range itself remains in state (a separate assertion reads `selection_range()` after the paint call and verifies it's unchanged). |
| AC9 | Read-only with selection paints the selection but *not* the caret; the read-only overlay (`read_only_overlay` brush, existing) is still emitted. Snapshot test `line_edit_read_only_selection.png` provides pixel-level evidence; a `RecordingPainter` unit test asserts the rect-count: selection-fill present, caret-fill absent, read-only-overlay present. |
| AC10 | Snapshot tests `line_edit_focused_empty.png`, `line_edit_focused_caret.png`, `line_edit_focused_selection.png`, `line_edit_unfocused_selection.png`, `line_edit_read_only_selection.png` exist under `quartzite-style/tests/snapshots/shared/` and pass `nv-flip` perceptual diff at `FLIP_TOLERANCE = 0.05`. Unit test asserts the captured brushes match (rect ordering: base-fill (pressed-inverted `Highlight`) → read-only-overlay-if-read-only → outline (`FocusRing` since focused) → main-text-draw (pressed `HighlightedText` brush) → selection-fill (Highlight × Normal) → selected-glyph overdraw (HighlightedText) → caret). ## Open questions

- **Caret painting under non-`Left` text alignment** — `LineEdit` currently passes `Alignment::Left` unconditionally to `draw_text_in` (`mod.rs:390`). If a future spec adds RTL or alignment-aware text on `LineEdit`, the caret-X computation needs to reflect the alignment (same open question as the TextEdit spec). Logged so the input-handling pass picks it up.
- **Horizontal-scroll-offset rendering when `text` overflows `geom.width()`** — single-line input traditionally scrolls horizontally so the caret stays visible. The current `draw_text_in` clips at `geom`; long text past the right edge is silently truncated. The selection-rect math via `text_carets` would return x-coordinates outside `geom` for selections past the right edge, and the painter clips them. Acceptable until a horizontal-scroll spec lands.
- **Password / masked input caret position exposure** — design-proposal *Open questions* §3: if a future `echo_mode` field masks the text, the caret cursor on the masked string would expose the byte index per cluster. Whether this is a privacy concern (e.g. revealing typing cadence through caret-x animation) is unspecified. Logged for the input-handling / password-mode follow-up.
- **Pressed-with-selection visual contract** — the design proposal does not specify this co-occurrence; the *Selection vs. pressed-state colour ladder* Key Decision applies the natural extension (selection-fill colour matches pressed-fill colour, producing a uniform Highlight band). A product-owner review of the AC12 unit-test fixture during code review can override this default without re-opening this spec.
