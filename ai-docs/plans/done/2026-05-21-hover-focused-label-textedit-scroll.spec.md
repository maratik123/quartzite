# Hover / pressed / focused rendering on Label / TextEdit / ScrollArea

**Source:** issue #403
**Date:** 2026-05-21
**Tracked in:** #403

> Surfaced by `/triage` from [`ai-docs/deferred/widget-backlog.md`](../../deferred/widget-backlog.md). Generalises the [`Button` hover / pressed / focused state-rendering pattern](../done/2026-05-15-button-hover-pressed-focused-states.spec.md) across `Label`, `TextEdit`, and `ScrollArea`. Event plumbing prerequisites are in place — `WidgetBase` carries `hovered` / `pressed` / `focused` flags, and `WidgetExt` exposes `is_hovered` / `is_pressed` / `is_focused` accessors. Only `DefaultStyle` paint impls change.
>
> The spec is written against the two-axis palette API (`palette.color(role, ColorGroup::{Normal, Hover, Pressed})` + `ColorRole::FocusRing`) shipped by the palette state-groups work, and against the post-migration `impl Paint<Button> for DefaultStyle` that already uses the same idiom (state-group selector + `maybe_disabled` + `FocusRing` outline at `FOCUS_RING_WIDTH = 2.0`). All APIs cited below exist on `master` and the Button impl is the established pattern reference.

## Scope

Add `hovered` / `pressed` / `focused` state-aware rendering to the existing `DefaultStyle` paint impls for `Label`, `TextEdit`, and `ScrollArea`, using the clean palette-state-groups API introduced by #402. The visual idioms follow [`design-system/README.md` § *Animation, hover, press*](../../../design-system/README.md) verbatim; the source-of-truth recipe is reproduced inline in § Key decisions below. The `Button` paint impl in `quartzite-style/src/default_style.rs` (post-#402) is the established pattern reference for how the state branches are wired.

Concretely:

- `impl Paint<Label> for DefaultStyle` in `quartzite-style/src/default_style.rs` reads `WidgetExt::is_hovered` / `is_pressed` / `is_focused` and produces the per-widget visuals decided in § Key decisions. Existing idle behaviour (`Window`-role fill + `WindowText`-role text in `w.alignment`) remains the baseline when all three flags are `false`.
- `impl Paint<TextEdit> for DefaultStyle` reads the same three flags and produces the per-widget visuals decided in § Key decisions. Existing idle behaviour (`Base`-role fill + 1 px `Text`-role outline + `Text`-role plain-text glyphs, with the read-only overlay still applied on top) remains the baseline. The `read_only` overlay logic is orthogonal — it applies in every state.
- `impl Paint<ScrollArea> for DefaultStyle` reads the same three flags and produces the per-widget visuals decided in § Key decisions. Existing idle behaviour (`Base`-role fill + 1 px `WindowText`-role outline) remains the baseline. The scrollbar-thumb / track work tracked separately under #315 stays out of scope.
- State resolution uses the `ColorGroup` axis: `let group = if w.is_pressed() { Pressed } else if w.is_hovered() { Hover } else { Normal };`, then every fill / text / pen lookup is `palette.color(role, group)`. No `Color::blend` arithmetic in the new paths — the blend lives inside `Palette::color`'s default derivation.
- Disabled (`!WidgetExt::is_enabled()`) treatment carries over via the existing `maybe_disabled` helper: every fill / text / non-focus-ring pen color computed by the new state paths goes through `maybe_disabled(color, enabled)` before being handed to the painter. Applied to all three widgets uniformly. **Exception: the `FocusRing` pen colour is exempt from `maybe_disabled`** — it always renders at full alpha per the design-system additive-overlay rule (`design-system/README.md` § *Animation, hover, press*: "never alpha-halved"), matching the shipped `impl Paint<Button>` behaviour.
- Focus outline reads `palette.color(ColorRole::FocusRing, ColorGroup::Normal)` for the pen stroke (per the design-system recipe); pen width is `2.0` (overrides the 1 px idle outline on `TextEdit` / `ScrollArea`; adds the 2 px outline on `Label` which has no idle outline). The `FocusRing` pen colour is NOT passed through `maybe_disabled` — it renders at full alpha even when the widget is disabled.
- Recording-painter unit tests in `quartzite-style/src/default_style_tests.rs` (one per visible state per widget, plus a `(disabled, focused)` precedence test per widget) toggle the matching flag on the widget's `WidgetBase` and assert the captured `Brush` / `Pen` matches the expected `palette.color(role, group)` value. Existing idle-state tests for the three widgets MUST still pass unchanged (flags default to `false`).
- Snapshot tests in `quartzite-style/tests/snapshots.rs` add one golden per visible state per widget under the existing `shared/` flow (light theme), plus one focused-state golden per widget under the existing dark-theme flow. Naming mirrors the Button pattern: `label_hovered.png`, `label_pressed.png`, `label_focused.png`, `text_edit_hovered.png`, `text_edit_pressed.png`, `text_edit_focused.png`, `scroll_area_hovered.png`, `scroll_area_pressed.png`, `scroll_area_focused.png`, plus dark `dark_label_focused.png`, `dark_text_edit_focused.png`, `dark_scroll_area_focused.png`.
- No `Style` / `Paint` trait surface redesign. The Button spec proved that per-widget state-awareness can be added directly inside each `Paint<W>` impl without touching the trait surface; with #402 in place the per-widget code shrinks further. If the design phase discovers a concrete trait-level need (e.g. a state-precedence helper shared across impls), it lands via a Design Amendment.

## Out of scope

- `LineEdit` hover / pressed / focused rendering. Tracked separately under [#406](https://github.com/maratik123/quartzite/issues/406) (deferred row in `widget-backlog.md`). The issue body and source spec deferred row both list only `Label` / `TextEdit` / `ScrollArea`; conflating the two issues would muddle the AC matrix.
- Scrollbar track / thumb rendering on `ScrollArea` (tracked under [#315](https://github.com/maratik123/quartzite/issues/315)). This spec only touches the chrome paint path; the eventual scrollbar work will need its own state-aware path on the thumb.
- New `ColorRole` variants beyond `FocusRing` (which lands in #402). No new roles introduced by this spec.
- Adding new `ColorGroup` variants beyond the three #402 introduces (`Normal` / `Hover` / `Pressed`). `Disabled` and `Focused` remain orthogonal modifiers per the #402 design.
- Event plumbing (renderer → widget tree). Hit-testing, `MouseEnter` / `MouseLeave` synthesis, focus traversal, and per-widget event routing are already handled by the prior input-plumbing pass (Button spec). Tests in this spec toggle the `WidgetExt::set_hovered` / `set_pressed` / `set_focused` setters directly on the widget's `WidgetBase`, exactly as the Button spec did.
- Mutating `WidgetBase::focus_policy` semantics. `Label` defaults to `FocusPolicy::NoFocus`; whether a focused-Label visual ever fires at runtime depends on the focus traversal pass and on whether the user opts the Label in via `focus_policy = StrongFocus`. The renderer paints whatever flag state it is given; AC tests toggle the flag directly regardless of policy.
- Cursor-shape changes on hover. Tracked under [#404](https://github.com/maratik123/quartzite/issues/404).
- TextEdit caret / selection / scroll-offset rendering. Tracked under [#317](https://github.com/maratik123/quartzite/issues/317).
- `Container` hover / pressed / focused rendering. `Container` is a grouping widget with no inherent interactive surface; not mentioned by the issue body. Defer to a separate issue if interactive-container semantics ever land.
- `Style` / `Paint` trait surface redesign. See § Scope final bullet.
- Re-aligning the `Button` paint impl with the two-axis palette API. That refactor already shipped with the palette state-groups work. This spec consumes the migrated Button impl as the established pattern reference and does not touch its body.

- Snapshot coverage for state combinations beyond single-flag goldens (e.g. `text_edit_focused_read_only.png`, `text_edit_disabled_focused.png`) | the Button spec capped at single-state goldens too; combinations are not enumerated unless a regression surfaces | follow-up if review flags a missing combo
- Re-paint trigger on state transition (calling `update()` after `set_hovered` / `set_pressed` / `set_focused`) | the input-plumbing pass owns the event-loop side and will set state + call `update()` together; this spec only changes paint output | input-plumbing pass
- Dark-theme `hovered` / `pressed` snapshot coverage on all three widgets | only `dark_*_focused.png` ships in v1 to keep the golden count proportional to the Button delta; `DARK_PALETTE` derives `Window` / `Base` Hover/Pressed cells via a small luminance shift toward `MERCURY` (0.06 / 0.16 blend), visually subtle relative to the Highlight-driven `Pressed` cells — the dark hover/pressed goldens for these chrome widgets would be near-identical to idle in this palette | follow-up only if a theme override surfaces visible divergence

## Key decisions

| Question | Decision |
|---|---|
| Where do the new render paths live | Inside the existing `impl Paint<Label> for DefaultStyle` / `impl Paint<TextEdit> for DefaultStyle` / `impl Paint<ScrollArea> for DefaultStyle` blocks in `quartzite-style/src/default_style.rs`. No new modules, no new public API on `Style` / `DefaultStyle`. Mirrors the Button spec's "Where the new render path lives" decision. |
| Scope of `Style` redesign | None. The shipped Button impl proves that per-widget state-awareness reduces to a one-line `ColorGroup` selector plus the existing two-axis palette lookups; the issue body's "likely a wider `Style` redesign" hedge does not apply with the two-axis palette API in place. If the design phase discovers a concrete trait-level pain point, it returns NO-GO with the proposed redesign as a Design Amendment. |
| Visual idioms — source of truth | **`design-system/README.md` § *Animation, hover, press*** + the shipped palette derivation rule from [`design-system/palette-state-groups.proposal.md` § *Default derivation*](../../../design-system/palette-state-groups.proposal.md). User answered all three Round-1 questions with "how design system describes it?", which the spec-writer reads as "the visual output must match the design-system text". The design-system recipe: `Hover = role × Hover` cell (default-derived as `c.blend(WindowText.Normal, 0.06)` inside `Palette::color`); `Pressed = Highlight × Pressed` fill + `HighlightedText × Pressed` text (role-swap + group lookup, both via the palette); `Focused = additive 2 px outline using `palette.color(ColorRole::FocusRing, ColorGroup::Normal)`; `Disabled = ×0.5 alpha applied after role/group resolution via `maybe_disabled` (unchanged). Per-widget rows below pin which paint primitives carry each flag. |
| Disabled-state interaction | Apply `maybe_disabled(color, enabled)` (already defined in `default_style.rs:274`) to every state-derived fill / text / pen color before painting, same as the shipped Button impl. Existing per-widget read-only / placeholder logic (TextEdit) stays orthogonal. |
| Snapshot test coverage shape | One golden per visible state per widget under `shared/` (light), plus one focused-state golden per widget under the existing dark-theme flow. Matches the Button pattern's coverage shape adjusted for the three widgets here. Concrete file list pinned under § Acceptance Criteria. |
| Recording-painter test layout | Each new state per widget gets a `#[test]` in `default_style_tests.rs` alongside the existing per-widget idle / read-only tests. Mirrors the Button spec's AC3–AC6 shape (toggle one flag, assert one Brush/Pen attribute matches the expected `palette.color(role, group)` value). |
| No new public API | `WidgetBase` / `WidgetExt` / `Style` / `Paint` / `DefaultStyle` public surfaces are unchanged. Only `impl Paint<…> for DefaultStyle` bodies change. The `ColorGroup` enum + `ColorRole::FocusRing` slot + two-axis `Palette::color` / `Palette::with_role` signatures already exist on `master`; this spec consumes them. |
| `Label` visual mapping | **Idle:** `palette.color(Window, Normal)` fill + `palette.color(WindowText, Normal)` text in `w.alignment` (shape unchanged; lookups already use the explicit `Normal` group on `master`). **Hover:** fill = `palette.color(Window, Hover)`; text = `palette.color(WindowText, Hover)`. **Pressed:** fill = `palette.color(Highlight, Pressed)`; text = `palette.color(HighlightedText, Pressed)` (role-swap matching the shipped Button-pressed). **Focused:** additive 2 px outline using `palette.color(FocusRing, Normal)`; base fill / text follow whichever of idle / hover / pressed applies. **Disabled:** every resolved colour passes through `maybe_disabled`. (Label has no outline at idle; the 2 px focus outline only paints when `focused` is set.) |
| `TextEdit` visual mapping | **Idle:** `palette.color(Base, Normal)` fill + 1 px `palette.color(Text, Normal)` outline + `palette.color(Text, Normal)` plain-text glyphs, with the read-only overlay still applied on top (shape unchanged; lookups already use the explicit `Normal` group on `master`). **Hover:** fill = `palette.color(Base, Hover)`; outline width 1 px, colour = `palette.color(Text, Hover)`; text colour = `palette.color(Text, Hover)`. **Pressed:** fill = `palette.color(Highlight, Pressed)`; text colour = `palette.color(HighlightedText, Pressed)`; outline width 1 px, colour = `palette.color(HighlightedText, Pressed)` (matches text for legibility under the inverted fill). **Focused:** outline widened to 2 px using `palette.color(FocusRing, Normal)`; fill / text follow whichever of idle / hover / pressed applies. **Read-only overlay applies on top of every state's fill** (orthogonal). **Disabled:** every resolved colour passes through `maybe_disabled`. |
| `ScrollArea` visual mapping | **Idle:** `palette.color(Base, Normal)` fill + 1 px `palette.color(WindowText, Normal)` outline (shape unchanged; lookups already use the explicit `Normal` group on `master`). **Hover:** fill = `palette.color(Base, Hover)`; outline width 1 px, colour = `palette.color(WindowText, Hover)`. **Pressed:** fill = `palette.color(Highlight, Pressed)`; outline colour = `palette.color(HighlightedText, Pressed)`. **Focused:** outline widened to 2 px using `palette.color(FocusRing, Normal)`; fill follows whichever of idle / hover / pressed applies. **Disabled:** every resolved colour passes through `maybe_disabled`. |
| State precedence (fill / text axis) | Carries over from the Button spec: `disabled` > `pressed` > `checked` > `hovered`. `checked` does not apply to Label / TextEdit / ScrollArea (none of the three has a `checked` flag), so the effective precedence on these three widgets is `disabled` > `pressed` > `hovered`. `focused` remains an additive outline modifier orthogonal to the fill axis (the Button impl's design carries over verbatim). |

## Technical constraints

- `quartzite-style` already depends on `quartzite-widgets`; the new code reads `WidgetExt::is_hovered` / `is_pressed` / `is_focused` exactly as the shipped Button impl does. No new dependency edges.
- The two-axis `Palette::color(role, group)` and `Palette::with_role(role, group, color)` signatures are the only palette APIs used by this spec. No direct `Color::blend` calls land in the new paint paths; the blend lives inside `Palette::color`'s default derivation.
- The existing `maybe_disabled` / `disabled` / `brush` / `read_only_overlay` helpers in `default_style.rs` are reusable as-is. (`maybe_disabled` accepts a `Color`, so it composes cleanly over the `palette.color(role, group)` lookups.)
- The existing `FOCUS_RING_WIDTH` const (`2.0`) in `default_style.rs` is reusable as-is for the 2 px focus outline; no new constant needed.
- The existing `RecordingPainter` fixture in `default_style_tests.rs` is reusable as-is for per-state Brush / Pen assertions.
- The existing snapshot harness (`quartzite-style/tests/snapshots.rs` + `tests/support/mod.rs`) is reusable — new tests follow the AC6 pattern from the Button spec.
- Doc gate: no new public items expected; the `RUSTDOCFLAGS="-D warnings -D missing-docs" cargo doc --no-deps --workspace --all-features` gate must stay clean.
- Lint gate: `cargo clippy --workspace --all-targets -- -D warnings` clean.
- File-size budget: `default_style.rs` is currently 280 lines; the three new state-aware paths SHOULD keep the file below the 500-line soft target. If the design phase finds it crowding 500, factoring helpers (e.g. `fn state_group`) out is fine.
