# Design: Widget System

**Issue:** #46
**Date:** 2026-05-08

## Approach

### New crate: `quartzite-widgets`

A new workspace member `quartzite-widgets` is created alongside the existing crates. It depends on
`quartzite-core`, `quartzite-macros`, `quartzite-geometry`, `quartzite-events`, and
`quartzite-paint-api`. It does not depend on `quartzite-runtime` — widgets themselves have no event
loop dependency; the runtime interacts with widgets through the `ObjectTree`. The facade crate
`quartzite` gets a new optional `widgets` feature that re-exports `quartzite-widgets`.

The crate requires `std` (via `quartzite-core/std`) because `Arc<Font>`, `Arc<Palette>`, and the
`Send` bound on `Object` together need the standard allocator and threading primitives. It is not
`no_std`.

### Hierarchy: `WidgetBase` as the hierarchy root

`WidgetBase` is the single hierarchy root for all widgets, mirroring the `ObjectBase`-rooted
pattern already in use. It is declared with `#[derive(Extend)] #[root]` (no `DeriveObject`) and holds an
`#[base] object: ObjectBase` field plus the widget-specific fields from the spec. This generates the
`AsWidget` trait and an `AsObject` delegation chain automatically. All concrete widgets declare
`#[base] widget_base: WidgetBase` (or chain further), receiving `AsWidget`, `AsObject`, and all
their methods for free.

`WidgetBase` does not derive `DeriveObject` because it has no properties of its own accessible via
`read_property`/`write_property` at the `WidgetBase` level — its fields are internal state exposed
only through concrete widget impls. Concrete widgets use `#[derive(Extend, DeriveObject)]` and
`#[object_impl]` as normal objects do.

### `WidgetExt` trait

`WidgetExt` is a non-object-safe blanket trait on all `AsWidget` types. It provides accessor
convenience methods (`geometry()`, `pos()`, `size()`, etc.) that read from `widget_base()` fields,
and lifecycle hooks with default no-op implementations. Default lifecycle hooks live on the trait
itself; concrete types override them inside their `#[object_impl]` block (or a regular `impl`
block, since they are not slots). The `update()` method sets `pending_update = true` on
`widget_base_mut()`.

### Layout system

`Layout` is a plain Rust trait (not an `Object`). Concrete layouts (`BoxLayout`, `GridLayout`) are
also `Object`s (they derive `Extend` and `DeriveObject`) and implement `Layout`. Widgets store a
`layout: Option<ObjectId>` in `WidgetBase`; the renderer resolves the `ObjectId` to a `&dyn
Object` and downcasts to `&dyn Layout` to call `set_geometry`. This avoids a `dyn Layout` fat
pointer in `WidgetBase` while keeping the layout swappable.

Because `quartzite-widgets` must not depend on `quartzite-runtime` (and thus has no access to
`ObjectTree`), `Layout::set_geometry` takes a resolver parameter:

```rust
pub trait WidgetResolver {
    fn resolve_widget_mut(&mut self, id: ObjectId) -> Option<&mut dyn AsWidget>;
}

pub trait Layout {
    fn set_geometry(&mut self, resolver: &mut dyn WidgetResolver, rect: Rect);
    fn size_hint(&self) -> Size;
    fn minimum_size(&self) -> Size;
}
```

`WidgetResolver` is a thin trait defined in `quartzite-widgets`; `quartzite-runtime` will implement
it on `ObjectTree` in plan #47 when the renderer wires layout passes. For tests in this plan, a
local `HashMap<ObjectId, WidgetBase>` struct implements `WidgetResolver` as an inline stub.

`BoxLayout` holds `Direction` (Horizontal/Vertical) and a `Vec<(ObjectId, i32)>` (child widget id
+ stretch factor). `GridLayout` holds a 2D cell map. Both implement `Object` via `#[object_impl]`.

### Concrete widgets

Each concrete widget (`Label`, `Button`, `LineEdit`, `TextEdit`, `ScrollArea`, `Container`) is a
`#[derive(Extend, DeriveObject)]` struct with `#[base] widget_base: WidgetBase`. Properties are
marked with `#[prop]`; signals with `#[signal]`; slots with `#[slot]` inside `#[object_impl]`.

Signals that carry a change value (e.g. `text_changed(String)`) are typed `Signal<(String,)>`.
The `clicked` signal on `Button` carries the checked state as its argument: `Signal<(bool,)>`.

### Alignment, FocusPolicy, SizePolicy, CursorShape enums

These four enums live in `quartzite-widgets` and derive `MetaEnum` so they participate in the value
system. They implement `Copy + Clone + Debug + PartialEq` and are used as property types inside
`WidgetBase` and `Label`.

### Font and Palette stubs

`Font` and `Palette` are `Send + Sync` structs with enough fields to satisfy the spec. Full font
rasterization and palette-driven theming are deferred to plan #47 (`quartzite-style`). Both are
stored via `Arc<Font>` / `Arc<Palette>` inside `WidgetBase` so multiple widgets can share a default
instance cheaply. An `Arc::make_mut` pattern allows per-widget overrides without cloning when
there is only one holder.

### Rejected alternatives

- **`add_widget`/`remove_widget` on the `Layout` trait (spec line 58):** The spec includes these
  methods on `Layout`. They are omitted from the trait because layout construction happens at call
  sites via struct fields (`BoxLayout { children: vec![(id, stretch)] }`) — not through a uniform
  `dyn Layout` interface. Moving mutation off the trait keeps the trait focused on geometry
  calculation only, which is all the renderer needs to call. This is a deliberate divergence; the
  spec methods can be added to concrete types (not the trait) if callers need them.
- **`WidgetBase` directly implements `Object`:** This would require `WidgetBase` to expose all
  widget-level properties through the base meta-object and would prevent concrete widgets from
  having their own properties in the same meta-system namespace. The per-concrete-type `Object`
  impl pattern (already used by every existing object) is the correct choice.
- **`Layout` stored as `Box<dyn Layout>` in `WidgetBase`:** Direct ownership couples `WidgetBase`
  to `Layout` at the type level and prevents sharing layouts across widget subtrees. The
  `ObjectId`-reference approach is consistent with how other objects are stored.
- **Separate `WidgetExt` extension trait crate:** YAGNI. A single `quartzite-widgets` crate with
  public `WidgetExt` in its root module is sufficient.

## Risks

- **`#[derive(DeriveObject)]` on `WidgetBase` with non-`IntoValue`/`FromValue` field types:**
  Fields like `Arc<Font>`, `Arc<Palette>`, `Option<ObjectId>`, `Vec<ObjectId>` must either be
  excluded from `#[prop]` or wrapped. `Arc<Font>` and `Arc<Palette>` are not properties; they are
  internal state not exposed via `read_property`. `ObjectId` is exposed as `Value::Object` /
  `Value::Int` depending on encoding — define `IntoValue`/`FromValue` for `ObjectId` in
  `quartzite-core` or skip exposing `layout` and `event_filters` as reflective properties.
  Mitigation: do not mark `font`, `palette`, `layout`, `event_filters`, `pending_update` as
  `#[prop]` in `WidgetBase`. They remain internal Rust fields. Only concrete widget props are
  exposed via `#[prop]`.
- **`Object: Send` bound propagation to `WidgetBase`:** `WidgetBase` must be `Send` for the
  `Object` supertrait. `Arc<Font>` and `Arc<Palette>` are `Send + Sync` as long as `Font` and
  `Palette` are `Send + Sync`. This is enforced by the `Arc` bounds. Mitigation: mark both `Font`
  and `Palette` with an explicit `static_assertions::assert_impl_all!(Font: Send, Sync)` or rely
  on the compiler to reject non-`Send` field types.
- **`#[derive(DeriveObject)]` does not support generic structs (enforced in parse.rs):** All
  widget types must be non-generic. This is consistent with existing objects in the codebase. No
  risk.
- **`WidgetBase` `#[root]` + `#[derive(Extend)]` requires `ObjectBase` as the `#[base]` field:**
  Per `extend/codegen.rs`, when the base field is `ObjectBase`, the macro emits direct field access
  (`&self.object`) for `AsObject`. This is the same pattern as `Timer` and every other root object.
  No risk.
- **`accessor_name("WidgetBase")` → `widget_base`:** Verified in `util.rs` tests:
  `strip_base_suffix("WidgetBase")` → `"Widget"`, `as_trait_name` → `"AsWidget"`,
  `accessor_name` → `"widget_base"`. The generated trait is `AsWidget`; accessor methods are
  `widget_base()` / `widget_base_mut()`. No risk.
- **`Layout` trait as a non-`Object` trait:** Downcasting from `&dyn Object` to `&dyn Layout`
  requires the resolver to call `downcast_ref::<BoxLayout>()` etc. Since there is no runtime type
  erasure of the `Layout` impl separately, the resolver must try each known layout type. This is
  acceptable for v1 (two layout types). Mitigation: if more layout types are added later, a
  `LayoutObjectExt` blanket trait can provide `as_layout(&self) -> Option<&dyn Layout>` via
  `Any` downcasting.
- **`Size::zero()` not yet on `Size`:** `WidgetExt::size_hint()` must return `Size::zero()`.
  Check whether `Size` has a `zero()` constructor. If not, `Size::default()` (which is
  `Size::new(0, 0)` per the `#[derive(Default)]` on `Size`) can be used instead, or a
  `Size::ZERO` const must be added. The `Size` struct derives `Default` (= zero-valued), so
  `Size::default()` is the safe fallback. Mitigation: use `Size::default()` in the trait default
  implementation; add `Size::ZERO` const in a follow-up annotation pass.
- **`pending_update` field flag semantics:** The spec says `update()` sets this flag; nothing in
  the current codebase clears it (rendering is deferred to plan #47). The flag is write-only from
  the widget side. No risk at this stage; the renderer will consume it in plan #47.
- **`event_filters: Vec<ObjectId>` without dispatch integration:** Event filters are stored but
  not dispatched in this plan. The open question from the spec about how filters are resolved at
  dispatch time is left open. Mitigation: store the `Vec<ObjectId>` as a plain field; dispatch
  integration is deferred.

## Test Design

### Task 4 — `WidgetBase`

- Location: `quartzite-widgets/src/widget_base.rs` `#[cfg(test)]`
- Entry points: `WidgetBase::new()`, `AsWidget::widget_base()`, `AsObject::object_base()`
- Scenarios:
  - New `WidgetBase` has `visible == false`, `enabled == true`, geometry is zero rect
  - `AsWidget` accessor returns correct self-reference
  - `AsObject` delegation returns the correct `ObjectBase`
- Fixtures: none; constructed inline

### Task 5 — `WidgetExt`

- Location: `quartzite-widgets/src/widget_ext.rs` `#[cfg(test)]` (or inline test in `widget_base.rs`)
- Entry points: `WidgetExt::show()`, `WidgetExt::hide()`, `WidgetExt::update()`, `WidgetExt::geometry()`, `WidgetExt::minimum_size()`
- Scenarios:
  - `show()` sets `visible = true` (AC4)
  - `hide()` sets `visible = false` (AC4)
  - `update()` sets `pending_update = true` (AC7)
  - `minimum_size()` returns `min_size` field (AC10)
  - `size_hint()` default returns `Size::default()`
- Fixtures: bare `WidgetBase` instance constructed directly

### Task 6 — `BoxLayout`

- Location: `quartzite-widgets/src/layout/box_layout.rs` `#[cfg(test)]`
- Entry points: `BoxLayout::set_geometry(Rect)`, `Layout::size_hint()`
- Scenarios:
  - Two widgets with equal stretch factor: each receives half the total rect width (AC5)
  - Single widget with non-zero stretch: receives the full rect
  - Empty layout: `set_geometry` is a no-op
- Fixtures: inline `HashMap<ObjectId, WidgetBase>` struct implementing `WidgetResolver` (no `quartzite-runtime` dependency needed)

### Task 7 — `GridLayout`

- Location: `quartzite-widgets/src/layout/grid_layout.rs` `#[cfg(test)]`
- Entry points: `GridLayout::set_geometry(Rect)`
- Scenarios:
  - Widget at (row=0, col=1) placed in correct cell rect (AC6)
  - Widget spanning 2 columns gets doubled width
- Fixtures: same inline `HashMap<ObjectId, WidgetBase>` stub resolver as BoxLayout tests

### Task 8 — `Label`

- Location: `quartzite-widgets/src/widgets/label.rs` `#[cfg(test)]`
- Entry points: `Object::read_property("text")`, `Object::meta_object()`
- Scenarios:
  - `meta_object().class_name == "Label"` (AC8)
  - `read_property("text")` returns `Value::String("hello".into())`
- Fixtures: `Label` constructed with a specific text

### Task 9 — `Button`

- Location: `quartzite-widgets/src/widgets/button.rs` `#[cfg(test)]`
- Entry points: `read_property("text")`, `write_property("text", …)`, `invoke_method("click", …)`
- Scenarios:
  - `read_property("text") == Value::String("OK".into())` after construction (AC1)
  - `invoke_method("click", &[])` emits `clicked` with `false` when not checkable (AC2)
  - `write_property("text", Value::String("Cancel".into()))` updates field and emits `text_changed` (AC3)
  - `write_property("text", same_value)` does not emit `text_changed` (idempotent guard)
- Fixtures: `Button` constructed with text "OK"; a spy closure connected to `clicked` and `text_changed`

### Task 10 — `LineEdit`

- Location: `quartzite-widgets/src/widgets/line_edit.rs` `#[cfg(test)]`
- Entry points: `invoke_method("set_text", …)`, `Signal::connect` on `text_changed`
- Scenarios:
  - `set_text("new")` when text differs emits `text_changed("new")` (AC9)
  - `set_text(same)` does not emit (idempotent guard)
  - `invoke_method("clear", &[])` sets `text = ""`
- Fixtures: `LineEdit` with initial text; a spy closure on `text_changed`

## Open questions

- `WidgetExt::paint` call convention: should `paint()` be called directly from test code or only
  via a renderer-side dispatch? The spec leaves this open. For v1, `paint()` is a default no-op in
  `WidgetExt`; concrete widgets override it. No dispatch mechanism is added in this plan.
- `event_filters` resolution at dispatch time: how are `ObjectId`s in `event_filters` resolved to
  `EventFilter` trait objects? This is out of scope for plan #46; it requires a design pass before
  any event-filter dispatch is implemented.
- `Container` vs bare `WidgetBase + layout`: should `Container` be a distinct type with its own
  meta-object, or is it just a `WidgetBase` with a `layout` set? The spec says "generic layout
  container with no visual chrome." A distinct `Container` type is a cleaner API surface (its own
  class name shows up in reflection, separate `Meta`). Recommendation: keep `Container` as a
  distinct type; it is trivial to implement and avoids ambiguity.
- `ObjectId` `IntoValue`/`FromValue`: the spec stores `layout: Option<ObjectId>` in `WidgetBase`.
  If `layout` needs to be exposed as a reflective property on concrete widgets, `ObjectId` must
  have `IntoValue`/`FromValue` impls. Currently, `ObjectId` is not a `Value` variant and
  `WeakObjectRef` is used for `Value::Object`. Decision: do not expose `layout` as a `#[prop]`
  in v1; it is internal state only. Revisit in plan #47.
