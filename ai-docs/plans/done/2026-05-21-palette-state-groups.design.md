# Design: Palette state groups — `ColorGroup` axis + `FocusRing` role

**Issue:** [#402](https://github.com/maratik123/quartzite/issues/402)
**Spec:** [`ai-docs/plans/2026-05-21-palette-state-groups.spec.md`](2026-05-21-palette-state-groups.spec.md)
**Proposal:** [`design-system/palette-state-groups.proposal.md`](../../design-system/palette-state-groups.proposal.md) (canonical reference for concrete RGBA values, derivation formula, swatch sheet)
**Date:** 2026-05-21

## Approach

### Chosen solution

A single-PR refactor of `quartzite-style-types` that introduces a `ColorGroup` axis orthogonal to `ColorRole`, adds a dedicated `ColorRole::FocusRing` variant, and reworks `Palette` storage and accessors to be two-dimensional. `Palette::new()` seeds every `(role, group)` cell at construction time via a closed-form derivation rule (`Hover = blend(c, WindowText.Normal, 0.06)`, `Pressed = blend(c, WindowText.Normal, 0.16)`), keeping `Palette::color` a `const fn` constant-time array lookup. `DARK_PALETTE` overrides only the cells that disagree with the derivation (none in v1 — every meaningful cell happens to land on the derived value). `DefaultStyle::draw_button` collapses the existing hover/pressed/checked precedence into a `(role, group)` lookup, removing the inline `Color::blend(_, _, 0.25)` heuristic from #316; every other `DefaultStyle` paint path migrates to the new two-arg `palette.color(role, ColorGroup::Normal)` signature. Snapshot goldens for `button_hovered` and `button_pressed` (light + dark) regenerate; the rest stay byte-identical.

### Why this approach

The spec's § *Key decisions* table already resolves every alternative-shape question (palette-vs-style for state colours, `ColorGroup`-vs-`ColorRole::HoverX` expansion, `Disabled`/`Focused`-as-`ColorGroup`, `FocusRing` location). This design picks the four remaining mechanical choices the spec defers to the design phase:

1. **`ColorGroup` location** — new file `quartzite-style-types/src/color_group.rs`, symmetric with `color_role.rs`. Each enum's exhaustive-match unit test lives next to the enum.
2. **`Palette` storage layout** — `[[Color; GROUP_COUNT]; ROLE_COUNT]` (a 2D array indexed `colors[role as usize][group as usize]`). Rationale: keeps `Palette::color` and `Palette::with_role` body to a single line each with no index arithmetic; clippy stays quiet (no `clippy::cast_possible_wrap` or arithmetic concerns); the per-role inner array is reachable via `colors[role as usize]` if we ever need it (we don't in v1). The flat `[Color; ROLE_COUNT * GROUP_COUNT]` with `role * GROUP_COUNT + group` alternative was considered and rejected — it requires hand-rolled index arithmetic in every accessor and offers no measurable win (the array is 36 × 16 bytes = 576 bytes either way, in-place `Copy`-bounded by `Clone`).
3. **Materialise the 8 derived-colour documentary names as `pub const` items on `Color`?** — **No.** They are documentary names for values the palette computes via derivation. Adding `Color::HOVER_WHITE` etc. ties the names to the public API surface (an irreversible extension once published), the values are already self-documenting at the point of use (`palette.color(ColorRole::Button, ColorGroup::Hover)`), and the per-theme `(role, group)` test assertions use either `Color::WHITE.blend(Color::BLACK, 0.06)` (derivation-computed) or `Color::new(0xF0_u8 as f32 / 255.0, 0xF0_u8 as f32 / 255.0, 0xF0_u8 as f32 / 255.0, 1.0)` (literal). (`Color::from_rgb_u8` does not exist.) This matches the spec's "defensible default".
4. **Snapshot diff presentation in AC11** — `cargo test --workspace` rebuilds the goldens; the regenerated files are committed in the same task that regenerates them. The PR body lists the exact set (`button_hovered.png`, `button_pressed.png`, `dark_button_hovered.png`, `dark_button_pressed.png`); the AC text already verifies mechanically (every other golden byte-identical). No additional tooling is required.

### Spec/reality drift discovered during investigation

The spec's AC11 names only the **light-theme** snapshot goldens that regenerate (`button_hovered.png`, `button_pressed.png`). The repository also commits `dark_button_hovered.png` and `dark_button_pressed.png` (generated by `dark_button_hovered_renders` / `dark_button_pressed_renders` in `quartzite-style/tests/snapshots.rs`). Both **will** regenerate under the new derivation:

- `dark_button_hovered.png`: old fill = `Color::ECLIPSE.blend(Color::DODGER_BLUE, 0.25)` (the #316 heuristic applied to the dark theme's `Button → Highlight` blend); new fill = `Color::ECLIPSE.blend(Color::MERCURY, 0.06)` ≈ `#464646` (`HOVER_ECLIPSE`). Visibly different RGB.
- `dark_button_pressed.png`: old fill = `Color::DODGER_BLUE` (= `Highlight × Normal`); new fill = `Color::DODGER_BLUE.blend(Color::MERCURY, 0.16)` ≈ `#3E9EFB` (`PRESSED_DODGER_BLUE`). Visibly different RGB.

Surfaced as an Open Question; the design plans for **both** light- and dark-theme goldens to regenerate. If product owner intends AC11 to mean "only light-theme goldens regenerate", the dark snapshot harness must be updated to keep the old behaviour — which contradicts the spec's "derivation is the only behaviour the framework commits to". The design proceeds with the regeneration of all four goldens; AC11 is read inclusively.

### Rejected alternatives

| Alternative | Why rejected |
|---|---|
| Flat `[Color; ROLE_COUNT * GROUP_COUNT]` storage with `role * GROUP_COUNT + group` indexing | Hand-rolled index arithmetic in every accessor for no measurable win. The 2D array reads identically in `const fn` context. |
| `[[Color; ROLE_COUNT]; GROUP_COUNT]` (transposed) storage | Less natural: a "palette with overrides for role X" mentally indexes role-first; group-first storage forces `colors[group][role]` in every accessor and breaks the "one row per role" mental model used by `DARK_PALETTE`. |
| Materialise `HOVER_WHITE`, `PRESSED_WHITE`, `HOVER_SKY_BLUE`, etc. as `pub const` on `Color` | Permanently extends the `Color` public API for documentary identifiers used only by tests. Reverts later require deprecation cycles (or a pre-publish API break). The `Palette` already computes the values; tests recompute via `Color::blend` or use `Color::new(r as f32 / 255.0, ...)` literals with no readability loss. (`Color::from_rgb_u8` does not exist.) |
| Compute derivation lazily on `Palette::color` access (no storage of derived cells) | Breaks `const fn` invariant (we'd need branching to detect "is this cell overridden?"). Also doubles read cost. The spec mandates "constant-time array lookup at call time". |
| Separate `Palette::role(role)` shorthand for `Normal` group | Spec's § *Key decisions* explicitly rules out adding it. Call sites use `palette.color(role, ColorGroup::Normal)`. |
| Run derivation only on `Palette::default` / `DARK_PALETTE` (not on `Palette::new()`) | Breaks the per-cell `Color::TRANSPARENT` invariant for hand-built palettes via `Palette::new().with_role(ColorRole::Button, ColorGroup::Normal, c)` — the other two group cells of that role would stay at `Color::TRANSPARENT`. Derivation in `new()` plus explicit overrides via `with_role` keeps the invariant cell-local. |
| Auto-rederive on `with_role` (recompute the role's two derived cells when `Normal` is overridden) | Surprising semantics: `palette.with_role(Button, Pressed, X).with_role(Button, Normal, Y)` would silently overwrite the `Pressed` override placed in the earlier call. Keep `with_role` as a literal cell setter; callers wanting "re-derive after changing Normal" use `with_role_all_groups`. |

## Risks

- **Risk:** `Palette::new()` running the derivation loop in `const fn` context exceeds the `const fn` budget once `ROLE_COUNT * 2 = 24` `Color::blend` calls compile-time-evaluate. **Mitigation:** `Color::blend` is `const fn` with a trivial body (4 lerps); the existing `DARK_PALETTE: Palette = Palette::new().with_role(...)` chain already runs 11 `with_role` calls at compile time without issue. The 24-call derivation loop is comparable; if the compile-time-eval budget triggers, drop the explicit loop in favour of an unrolled per-role `with_role_all_groups`-style construction (Tasks 3+4 already pre-seed every Normal cell explicitly, so the loop scope is bounded). Validation: build `cargo build -p quartzite-style-types` after Task 3 and confirm no `error[E0571]` / "evaluation of constant value failed" diagnostic.
- **Risk:** `[[Color; GROUP_COUNT]; ROLE_COUNT]` storage triggers a clippy `large_stack_arrays` or `large_const_array` lint as cells grow from 11 to 36. **Mitigation:** 36 × 16 bytes = 576 bytes — well under the workspace's `large-stack-arrays` clippy threshold (default 512 000 bytes). Verified by inspection; no `clippy.toml` override on this lint.
- **Risk:** A downstream caller this design did not enumerate uses the old single-arg `palette.color(role)`. **Mitigation:** AC12 mandates `rg 'palette\.color\([^,]+\)\|with_role\([^,]+,[^,)]+\)' -t rust` returns zero hits. Task 5 ends with an `rg` sweep covering every `quartzite-*/src/` and `quartzite-*/tests/` path. If a hit surfaces in a workspace member the design missed (`quartzite-renderer`, `quartzite-app`, `examples/`), migrate it in the same task before commit.
- **Risk:** `dark_button_hovered.png` / `dark_button_pressed.png` regenerate but the spec's AC11 names only the light-theme goldens. **Mitigation:** Surfaced as an Open Question. The proposal's § *Default derivation* paragraph 3 explicitly commits to derivation being "the only behaviour the framework commits to" in both themes, which forces the dark goldens to regenerate. The design treats both light and dark regeneration as in-scope; the PR body enumerates the full 4-file set.
- **Risk:** `default_style_tests.rs` test churn is large enough to make the diff hard to review (≈ 80 lines of `palette.color(role)` → `palette.color(role, ColorGroup::Normal)`). **Mitigation:** Task 5 is mechanical; the diff splits naturally — the signature-migration sub-diff is rote substitution (reviewable by sampling), the test-rewrite sub-diff is localised to four named tests (`hovered_button_uses_blended_fill`, `pressed_button_uses_highlight_roles`, `precedence_focused_hovered_blend_plus_outline`, `focused_button_uses_2px_highlight_outline`) plus one new test (`pressed_and_checked_button_picks_highlight_pressed`).
- **Risk:** `Palette::with_role` losing `const fn` because the derivation closure isn't `const`-friendly. **Mitigation:** `with_role` is a single-cell write (`self.colors[role as usize][group as usize] = color; self`), no derivation — stays `const fn` trivially. Derivation runs only in `Palette::new()`. `with_role_all_groups` writes three cells in sequence — also `const fn`-compatible.
- **Risk:** Snapshot regeneration on the agent's machine produces goldens that disagree with the CI runner's GPU output (the GPU-rendering harness can shift sub-pixel rounding across drivers). **Mitigation:** The existing `quartzite-style/tests/snapshots/{shared, vulkan, auto}/` subdirectory structure already pre-supposes per-backend goldens. Task 6 regenerates whichever directory the agent's local backend writes; if CI hits a mismatch on a different backend, the `/pr-ci-failed` skill handles regeneration on that backend. No new infrastructure needed.

### Task 3 — `Palette` refactor

- **Location:** existing `quartzite-style-types/src/palette.rs` `#[cfg(test)] mod tests`.
- **Entry point:** `Palette::new`, `Palette::default`, `Palette::color`, `Palette::with_role`, `Palette::with_role_all_groups`.
- **Scenarios:**
  - **AC6** `every_cell_of_default_is_non_transparent` (extend existing `default_has_non_transparent_color_for_every_role`): nested loop over `ColorRole::ALL × ColorGroup::ALL`, assert each `palette.color(*role, *group) != Color::TRANSPARENT`.
  - **AC7** `light_palette_meaningful_state_cells`: assert exact RGBA for the five meaningful cells. `Color::from_rgb_u8` does **not** exist on `Color`; use `Color::WHITE.blend(Color::BLACK, 0.06)` (mirrors the derivation) for hover assertions, or construct via `Color::new(0xF0_u8 as f32 / 255.0, 0xF0_u8 as f32 / 255.0, 0xF0_u8 as f32 / 255.0, 1.0)` for a literal comparison. All assertions use `==` on `Color` (exact float equality is safe because the derivation is deterministic `const fn`); if float rounding causes instability, assert each component within `0.5 / 255.0` tolerance. Apply the same pattern for `Button × Pressed`, `Highlight × Hover`, `Highlight × Pressed`, `FocusRing × Normal`.
  - **AC7** `light_palette_derivation_applies_to_all_cells` (replaces the "mirror" scenario per Spec Amendment — byte-for-byte mirror is not the contract; derivation is): pick a role that is not in the meaningful-cells list (e.g. `Window`) and assert `palette.color(ColorRole::Window, ColorGroup::Hover) == Color::WHITE.blend(Color::BLACK, 0.06)` — verifying the derivation formula ran, not that the cell is unchanged. For roles like `Text × Hover` where `Normal == BLACK == WindowText.Normal`, derivation coincidentally produces the same value: assert `palette.color(ColorRole::Text, ColorGroup::Hover) == Color::BLACK` (demonstrates formula correctness for a foreground role).
  - **AC4** `color_returns_constant_time_lookup`: smoke test — call `palette.color(ColorRole::Button, ColorGroup::Hover)` and assert it equals the directly-indexed cell `palette.colors[ColorRole::Button as usize][ColorGroup::Hover as usize]` (if the field is exposed via a test-only `pub(crate)` accessor, or by checking that two consecutive calls return identical values).
  - **AC5** `with_role_replaces_single_cell`: extend the existing `with_role_replaces_slot_only` test for the new three-arg signature.
  - **AC5** `with_role_all_groups_replaces_all_three_cells`: `let p = Palette::default().with_role_all_groups(ColorRole::Button, Color::RED); assert!(ColorGroup::ALL.iter().all(|g| p.color(ColorRole::Button, *g) == Color::RED));` plus a spot check that an unrelated role is untouched.
  - **AC5** `with_role_chains` (extend the existing test for the new signature).
  - **AC6** `palette_new_seeds_focus_ring_to_sky_blue`: `assert_eq!(Palette::new().color(ColorRole::FocusRing, ColorGroup::Normal), Color::SKY_BLUE)`.
  - **AC7** `focus_ring_per_group_cells_mirror_normal` (new — enforces spec § *Out of scope* FocusRing carve-out): `assert_eq!(Palette::default().color(ColorRole::FocusRing, ColorGroup::Hover), Palette::default().color(ColorRole::FocusRing, ColorGroup::Normal))` and the same for `Pressed`. These pass because Task 3 calls `with_role_all_groups(FocusRing, SKY_BLUE)` after the derivation loop.
  - **Const-eval guard**: `const _: Color = Palette::new().color(ColorRole::Button, ColorGroup::Normal);` — verifies the new `color` accessor stays `const fn`-callable.
- **Fixtures / helpers:** `Color::new(r as f32 / 255.0, g as f32 / 255.0, b as f32 / 255.0, 1.0)` for literal RGBA assertions; `Color::blend` for derivation-computed expected values. (`Color::from_rgb_u8` does not exist in `quartzite-paint-api`.)
