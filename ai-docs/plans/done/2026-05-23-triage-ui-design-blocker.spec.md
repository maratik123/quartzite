# /triage UI-design blocker gate

**Source:** user description (free-text)
**Date:** 2026-05-23
**Tracked in:** #545

## Scope

1. Extend `/triage` (skill: `.claude/skills/triage/SKILL.md` + agent: `.claude/agents/triage-runner.md`) so every gh issue it creates is classified as either **needs-design-work** or **plain** before `gh issue create` runs.
2. **Classification trigger (Hybrid keyword + LLM auto-detect fallback).** For each row entering the Phase 7.5 create-queue, `triage-runner` performs a case-insensitive substring scan of the row's `Item` cell text concatenated with the row's `Source spec` filename against a hard-coded keyword list (see Technical constraints #2 for the list and its location). Two outcomes:
   - **Hit** → emit a y/n confirmation prompt: *"Row matches design-work keyword `<hit>` — classify as design-work and require ui-design umbrella link? (y/n)"*. The y answer continues into the umbrella-selection prompt below; n marks the row plain and skips the gate.
   - **No hit → LLM auto-detect.** Instead of prompting "Classify as design-work anyway? (y/n)" with no pre-classification, the `/triage` orchestrator (Claude itself; `/triage` already runs inside Claude Code) reads the row's `Item` cell text AND the relevant section of the row's `Source spec` file, and INFERS a design-work classification. The orchestrator then emits a single y/n confirm prompt with the inference as the default: *"Auto-classification: `<DESIGN-WORK | PLAIN>` (reason: `<one-line summary>`). Accept? (y/n)"*. The y answer honours the inference (continues to umbrella-selection if `DESIGN-WORK`, skips the gate if `PLAIN`); n flips to the other classification. No external API plumbing — uses the orchestrator's own LLM context.
3. **Umbrella-selection prompt (design-work rows only).** Discovery uses the Phase 4 dedupe map filtered to `state=OPEN` AND `labels` contains `ui-design`. **Ranking:** the numbered menu is ordered by keyword-overlap between (the row's `Item` cell text) and (each umbrella's title + body), using the same hard-coded keyword list from Technical constraint #2 as the overlap signal — a shared keyword (case-insensitive substring hit) on both sides counts +1; a shared NON-keyword token does not count (avoids generic noise like "the", "and", "a"). Sort umbrellas by descending overlap score; ties broken by `#N` ascending (oldest first). The menu still shows ALL open `ui-design` umbrellas — ranking only affects ORDER. Presentation: a numbered menu (1..N) of `#<num> <title> — <truncated body summary>`, followed by text options `new` / `none` / `defer`. User picks one of:
   - **Numbered pick (1..N)** → link the row's new issue to the chosen umbrella by applying the `blocked` label + the `ui-design` label and prepending a `**Blocked by:** #<umbrella>` line to the new issue's body (matches the convention the 4 existing umbrellas `#539`, `#540`, `#541`, `#542` already use for children). **Additionally**, `/triage` fetches the umbrella body via `gh issue view <umbrella-N> --json body`, locates the `## Child issues (blocked on this epic)` section anchor, and appends a new bullet `- #<child-N> — <child-title>` at the end of the section's bullet list (immediately before the next h2 heading OR end-of-body), then pushes the edited body back via `gh issue edit <umbrella-N> --body-file <tmpfile>` (see Technical constraint #8 for anchor / idempotency / fallback rules).
   - **`new`** → `/triage` collects the new umbrella's title and body from the user via two follow-up prompts (`Umbrella title:` / `Umbrella body:`), creates the umbrella inline in the same Phase 7.5 bulk pass with the `ui-design` label, captures the returned `#N`, and then links the row's issue to that `#N` using the same labels + `**Blocked by:** #N` body line as the numbered-pick branch. **Additionally**, the same child-checklist body edit described above is performed against the newly-created umbrella (per Technical constraint #8).
   - **`none`** → create the row's issue with no `blocked` / `ui-design` / `**Blocked by:**` link. Recorded in the Phase 8 run summary as a "design-work issue without umbrella link"; the row is still created. No umbrella body edit.
   - **`defer`** → do NOT create the row's gh issue. The row is returned to `_inbox.md` (or left there if it was already there) for a future `/triage` run; the deferral is recorded in the Phase 8 summary. No umbrella body edit.
4. **Gate ordering.** The gate fires AFTER the row is classified as ready-to-promote (Phase 6 sweep approval / Phase 7 drain promote) but BEFORE the row's `gh issue create` call inside Phase 7.5. This ensures a newly-created umbrella's `#N` is available to be cited in the row issue's `**Blocked by:** #N` body line.
5. **`/next` SKILL.md propagation on umbrella mutation.** Every `/triage` run that mutates the open-`ui-design` umbrella set — either by inline-creating a new umbrella (via the `new` branch) OR by widening an existing umbrella (linking a new child to it via numbered pick) — MUST, in the same `/triage` run, perform a Triage-group propagation step against `.claude/skills/next/SKILL.md`: (a) grep the file for any specific umbrella `#N` references that became stale as a result of the mutation (currently expected to return zero hits because the post-PR-#544 SKILL.md queries umbrellas dynamically via `gh issue list --label ui-design` and does NOT enumerate specific umbrella numbers); (b) if the user / maintainer wishes, edit the SKILL.md *UI-designer label* mini-section (currently lines 95–101) or the `## Candidates for UI-designer handoff` output bullet (currently line 119) in the same run to mention the new / widened umbrella by example — this is permitted but not required. The propagation step is mandatory; the edit itself is optional. The result of the grep is recorded in the Phase 8 run summary.

## Out of scope

1. **Retroactively re-classifying gh issues already created prior to this change AND the 277 existing rows in `_inbox.md` are out of scope.** The gate applies only to NEW rows passing through `/triage` going forward. The bridge sweep (Phase 4.5) does NOT grow a new conflict type for "design-work issue lacks `ui-design` umbrella link" on legacy rows / issues.
2. **Static (spec-merge-time) edits to `.claude/skills/next/SKILL.md`.** At the time this spec lands, `/next` does not create gh issues and the post-PR-#544 SKILL.md queries umbrellas dynamically — no edit is needed AT SPEC-MERGE TIME and the propagation grep is confirmed-empty (recorded in AC6). However, this does NOT cover the **dynamic per-umbrella-mutation propagation step** introduced in Scope item 5: that step fires at `/triage` RUNTIME, every time `/triage` creates or widens an umbrella, and is in scope. The distinction is: this spec's diff does not edit `next/SKILL.md`, but the `/triage` runtime behaviour added by this spec will perform the grep (and optionally an edit) on every umbrella-mutating run going forward.

## Technical constraints

1. **Triage-group propagation (bidirectional: spec-merge-time + `/triage`-runtime).** Two distinct propagation duties apply.
   - **Spec-merge-time (this PR's diff).** Edits to `.claude/skills/triage/SKILL.md` and `.claude/agents/triage-runner.md` must stay in lock-step per AGENTS.md Propagation Rule. `.claude/skills/next/SKILL.md` is grep-checked but unchanged at this point (no `gh issue create` happens in `/next`; the post-PR-#544 SKILL.md queries umbrellas dynamically via `gh issue list --label ui-design` and enumerates no specific umbrella numbers). The propagation grep is the AGENTS.md-mandated step before commit.
   - **`/triage`-runtime (every umbrella-mutating run).** Per Scope item 5 / Key Decisions Q10, every `/triage` run that inline-creates a new `ui-design` umbrella OR widens an existing umbrella (links a new child to it) MUST grep `.claude/skills/next/SKILL.md` in the same run for stale specific-umbrella references and MAY edit the *UI-designer label* mini-section (current lines 95–101) or the `## Candidates for UI-designer handoff` output bullet (current line 119) to mention the new / widened umbrella by example. The grep is mandatory; the edit is optional; the grep result is recorded in the Phase 8 run summary.
2. **Keyword list (initial set, case-insensitive substring match). Dual role.** Lives inside `.claude/agents/triage-runner.md` adjacent to the gate code. Initial entries: `style`, `paint`, `palette`, `colorrole`, `widget`, `chrome`, `visual`, `theme`, `snapshot`, `Highlight`, `FocusRing`, `caret`, `selection`, `scrollbar`, `popup`, `tooltip`, `dialog`, `modal`, `icon`, `font`, `IME`, `RTL`, `BiDi`. **Role (i) — classification trigger:** matched case-insensitively against the row's `Item` cell text concatenated with the `Source spec` filename to drive the hit / no-hit branch of Scope item 2. **Role (ii) — ranking signal:** the same list is used as the overlap signal for ranking the umbrella numbered menu per Scope item 3 / Key Decisions Q13. A shared keyword (case-insensitive substring hit on both the row's `Item` text AND the umbrella's `title + body`) counts +1 toward the overlap score; a shared NON-keyword token does not count. The design phase MAY extend / reorder the list with rationale; the spec lists this as the minimum starting set.
3. **No new `gh issue list` calls** — the bulk Phase 4 call already returns a dedupe map; the `--json` flag list is extended from `number,state,title` to `number,state,title,labels,body`. `body` is added so the umbrella-overlap ranking (per Tech constraint #2 role (ii)) can score against the umbrella body without a second round-trip. Map shape goes from `{number → {state, title}}` to `{number → {state, title, labels, body}}`. The pagination watchdog (≥ 450) and the "one bulk call per run" contract are preserved.
4. **Progress-file schema** — the per-row record inside the Phase 6 / Phase 7 partition section gains a `design_link:` sub-field whose values are exactly one of: `none` (plain row, gate did not apply), `umbrella=#N` (linked to existing umbrella picked from the numbered menu), `umbrella=#N (new)` (linked to a newly-created umbrella; the `#N` is the new umbrella's number), `skip-link` (`none` chosen at umbrella prompt — issue created without umbrella link), `defer` (row deferred via `defer` option — no issue created). Resume from a partly-prompted partition must NOT re-prompt for already-recorded design-link decisions; mirrors how Phase 4.5's per-conflict resolutions are appended.
5. **Rule-5 substring** — the spec body necessarily references the `blocked` label and `Blocked by:` body convention because that IS the mechanism being implemented. This is prescribed input from the issue body (Round-1-confirmed), not a question to surface. The orchestrator-owned Rule-5 enforcement (spec-writer must not ASK about it) is unaffected.
6. **AskUserQuestion mid-run is already in-character** for `/triage` — Phase 6 batched table, Phase 7 drain per-row, Phase 4.5 per-conflict resolution. Adding one classification prompt (+ a follow-up umbrella prompt when classified design-work, + two title/body prompts for the `new` branch, + the LLM-inference y/n confirm on no-hit) per design-classified row fits the existing UX shape.
7. **LLM auto-detect on no-hit — prompt shape + read-scope.** When the keyword scan returns no-hit, the `/triage` orchestrator (Claude Code itself) reads (i) the row's `Item` cell text + (ii) the row's `Source spec` file, restricted to the spec section referenced by the deferred row's source coordinates (NOT the whole repo, NOT every spec in the repo — read budget is bounded by one spec file's worth of context). The orchestrator infers a `DESIGN-WORK | PLAIN` classification + a one-line reason, then emits exactly one y/n confirm prompt of shape *"Auto-classification: `<DESIGN-WORK | PLAIN>` (reason: `<one-line summary>`). Accept? (y/n)"*. `y` honours the inference (continues to umbrella-selection if `DESIGN-WORK`; skips the gate if `PLAIN`). `n` flips to the other classification (continues to umbrella-selection if the flip is `DESIGN-WORK`; skips the gate if the flip is `PLAIN`). No external API plumbing — the orchestrator uses its own LLM context. The inference + accept/flip outcome is captured in the progress file under the `design_link:` sub-field's audit trail.
8. **Umbrella child-checklist auto-update — anchor + idempotency + fallback.** When a row's new gh issue is linked to an umbrella (numbered pick OR `new`-branch newly-created), `/triage` calls `gh issue view <umbrella-N> --json body` to fetch the umbrella body, locates the section anchor `## Child issues (blocked on this epic)` (verbatim — this is the convention `#539`, `#540`, `#541`, `#542` already use; see those umbrella bodies as references), and appends a new bullet `- #<child-N> — <child-title>` at the END of that section's bullet list — placed immediately before the next h2 (`## …`) heading if one follows the section, OR at end-of-body if the section is the final h2. The edited body is pushed back via `gh issue edit <umbrella-N> --body-file <tmpfile>`. **Idempotency:** if a bullet `- #<child-N> — …` already appears under the same section anchor (substring match on `#<child-N> `, with the space-after-number sentinel to avoid `#54` matching `#549`), the edit is a no-op and `/triage` proceeds without writing. **Fallback when the anchor is absent:** rare (user-created umbrellas may diverge from the #539–#542 convention). In that case, `/triage` emits a single warning *"Umbrella #<umbrella-N> has no `## Child issues (blocked on this epic)` anchor — skipping auto-update"* + skips the body edit + falls back to a per-umbrella reminder in the Phase 8 summary (AC6 fallback path). The fallback fires per umbrella, not per row.

## Open questions

- **OQ1 (low-leverage; design-phase defendable).** Should the Phase 8 "Design-link outcomes" sub-section be machine-parseable (e.g. for a future `/next`-side audit of umbrella → child consistency)? Defensible default: free-form markdown list mirroring the bridge sub-section. Design phase decides.
- **OQ2 (low-leverage; design-phase defendable).** If the user picks a numbered umbrella whose `state` flipped to `CLOSED` between Phase 4's dedupe-map snapshot and Phase 7.5 (rare; possible if bridge sweep hasn't reconciled this session), what happens? Defensible default: filter the umbrella list to `state=OPEN` only at presentation time (per Q3 / Tech constraint #3) so closed umbrellas don't surface. If a race still occurs (closed between map snapshot and prompt), the `gh issue create` call still succeeds and the umbrella body edit still applies — the closed umbrella becomes the parent regardless. Design phase confirms whether to add a freshness re-check.
