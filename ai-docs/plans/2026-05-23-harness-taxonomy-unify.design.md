# Design: Harness taxonomy unify — Tools / Subagents / Skills / Hooks

**Issue:** #547
**Date:** 2026-05-23

## Approach

This is a prose-only, instruction-file refactor across the in-scope corpus that this project loads as instructions (per the 40k AXIOM `AGENTS.md` § Build & Test). The spec is 21-AC strong, fully pre-resolved (no open questions), and the work decomposes into three deliverable clusters:

1. **Canonical-doc preparation** — `ai-docs/claude-tools-hierarchy.md` becomes the single source of truth with frozen anchors plus a new embedded-`verify` row in §3a. This MUST land first (or first-in-PR-graph) because every other file's on-demand pointer + every inbound deep-link assumes the stable anchors and the §3a / §3c shape are in place.
2. **AGENTS.md core changes** — the new clash-rename AXIOM (AC16), the new Propagation Rule sync-group row (AC10), and offsetting shrinkage to satisfy AC9 (AGENTS.md ≤ 36,808). Done in one focused subtask to keep all AGENTS.md edits visible together for char-budget review.
3. **Corpus sweep + verify rename** — the four-axis sweep across `.claude/skills/`, `.claude/agents/`, `.claude/rules/`, root markdown, and `ai-docs/` (split by directory for handoff focus), plus the `verify` → `verify-change` folder rename + 4 inbound-reference updates + post-rename clash-scan baseline, plus the `/ai-audit` Checklist O addition.

**Why this ordering.** The canonical doc must stabilise its anchor surface before siblings deep-link to it (otherwise the `<!-- stable-anchor: #x -->` markers carry no enforcement loop and any new pointer added during the sweep risks pointing at a heading that may shift). The §3a embedded-`verify` row addition (AC21) belongs in the same subtask because §3a is in the same file and the §3c rename (AC18) reads cleanly only once §3a documents the embedded `verify`. AGENTS.md changes go second so AC9's hard size guard for AGENTS.md (36,808 ceiling) can be enforced with full visibility into the AXIOM-block char cost before the rest of the corpus sweep churns ancillary files.

**Rejected alternative — single bulk-sweep.** Treating every file as interchangeable and applying terminology rewrites in one pass risks (a) breaking dual-model-readability by losing per-skill voice (AGENTS.md Communication AXIOMs vs. `/task` Step-by-step procedural text vs. `learnings-escalation-audit.md` checklist tone — each requires careful per-file review), (b) failing AC9 silently because the AXIOM-block additions to AGENTS.md may eat budget that other AGENTS.md edits also wanted to spend, and (c) churning git diff readability for review. Per-directory grouping keeps each handoff focused on ≤ 6 files.

**Rejected alternative — defer the `verify` rename to a separate PR.** Spec § Round-3 binds the rename to this PR; AC18 + AC19 are pass gates. Deferral would also leave AC19's "clash-scan baseline passes" non-passing because the embedded-`verify` row addition (AC21) ships in this PR and would create a clash with the un-renamed project `verify` Skill if AC18 were dropped. The two ACs are co-dependent — they ship together.

**Rejected alternative — extract AGENTS.md taxonomy paragraphs to a brand-new `ai-docs/taxonomy.md` file.** The spec already designates `ai-docs/claude-tools-hierarchy.md` as the canonical doc and AGENTS.md has no large taxonomy paragraphs to extract (its taxonomy mentions are short — `## Agent Docs` row, the "skill vs agent" sentence, AGENTS.md banner). The shrinkage offset that AC9 requires comes from compacting the new AXIOM block, not from large extractions.

### Stable-anchor implementation pattern (resolves AC11 slug-match correctness)

GitHub-flavoured-markdown auto-slugging of the canonical doc's load-bearing headings produces slugs that DO NOT all match the AC11 stable-anchor set verbatim. Verified against the live `claude-tools-hierarchy.md` heading list at design time:

| Heading line in canonical doc | GFM auto-slug | AC11-listed anchor | Match? |
|---|---|---|---|
| `## 1. Tools` | `#1-tools` | `#1-tools` | YES |
| `## 2. Subagents (via \`Agent\` tool)` | `#2-subagents-via-agent-tool` | `#2-subagents` | **NO** |
| `## 3. Skills (via \`Skill\` tool or typed \`/<name>\`)` | `#3-skills-via-skill-tool-or-typed-name` | `#3-skills` | **NO** |
| `## 4. Hooks` | `#4-hooks` | `#4-hooks` | YES |
| `## Mental model` | `#mental-model` | `#mental-model` | YES |
| `## Stable anchors` (new) | `#stable-anchors` | `#stable-anchors` | YES |

**Decision — Option B (explicit HTML anchors, recommended by reviewer).** Keep the existing heading text verbatim (preserving the in-heading context "via `Agent` Tool" / "via `Skill` Tool or typed `/<name>`" which carries dual-model-readability value) and add an explicit HTML anchor element immediately above each load-bearing heading. Rejected Option A (shorten headings to `## 2. Subagents` / `## 3. Skills`): loses the syntactic context "via `Agent` Tool" inline at the heading, forcing readers to scroll into body text to learn the dispatch mechanism — degrades skim-readability for both human and dual-model agents.

**Pattern (applied to all 6 load-bearing headings):**

```markdown
<!-- stable-anchor: #2-subagents -->
<a id="2-subagents"></a>
## 2. Subagents (via `Agent` Tool)
```

Two pre-heading lines:

- **Line 1** — `<!-- stable-anchor: #<slug> -->` HTML comment (the AC11-mandated marker; lives FIRST so a diff viewer surfaces it before the heading line below).
- **Line 2** — `<a id="<slug>"></a>` explicit HTML anchor element. This is the load-bearing element that makes inbound `[…](claude-tools-hierarchy.md#<slug>)` deep-links resolve regardless of how the GFM auto-slug for the heading evolves.

Both lines sit **immediately above** the heading (no blank line between them and the heading) so future editors see the comment marker FIRST in their diff viewer and the anchor element SECOND before touching the heading text. (Pinning the placement here resolves Minor #5 — three different positional phrasings ("above" / "beside" / "next to") in spec + round-1 design collapse to ONE: *immediately above the heading line, in marker-then-anchor order, no separating blank line*.)

For headings whose GFM auto-slug already matches the stable-anchor set (`#1-tools`, `#4-hooks`, `#mental-model`, `#stable-anchors`), the `<a id="…"></a>` element is technically redundant but is added uniformly anyway — uniformity makes the pattern self-documenting and protects against future heading-text drift that would silently break slugs (e.g. someone renaming `## 4. Hooks` to `## 4. Hooks (event types)` would otherwise break inbound `#4-hooks` deep-links without the explicit anchor).

**Heading-text capitalisation fix bundled with the same edit (resolves Minor #3).** Even with Option B preserving heading text structurally, the *intra-heading* Tool/tool capitalisation hits MUST be normalised for AC1 consistency on the canonical doc itself. Three sites confirmed by the design-time `grep -nE 'LSP tool|the (Bash|...) [Tt]ool|via .?(Agent|Skill).? [Tt]ool'` (see *Pre-flight measurements* below for the verbatim grep output):

- Line 47: `## 2. Subagents (via \`Agent\` tool)` → `## 2. Subagents (via \`Agent\` Tool)`
- Line 75: `## 3. Skills (via \`Skill\` tool or typed \`/<name>\`)` → `## 3. Skills (via \`Skill\` Tool or typed \`/<name>\`)`
- Line 205: `LSP tool` (inside a code-block diagram, used as the target of a dispatch arrow) → `LSP Tool`. Line-8 referenced by round-1 review-feedback was a false positive on inspection (no LSP-tool hit at line 8; design-time grep returns line 205 only — the round-1 review's "line 8" citation was an aliasing artifact). The single LSP-tool hit at line 205 is included in subtask 1's batch.

All four heading/body rewrites land in subtask 1's single commit.

**Deliberate retention (acknowledges reviewer's recommendation about AC1 enforcement-spirit).** The phrases *"matching tool call"* at lines 138 + 148 (`### 4b. \`PreToolUse\` 🟩 — fire **before** a matching tool call` / `### 4c. \`PostToolUse\` 🟩 — fire **after** a matching tool call`) use the lowercase word `tool` as a generic noun describing a class of harness events (any Tool can be matched), NOT as a synonym for a specific Tool name. The AC1 substring blacklist regex `\bthe (bash|read|write|edit|agent|skill|grep|glob) tool\b` deliberately excludes generic `tool` usage; these phrases pass the regex and are retained verbatim as a deliberate retention. Subtask 1 documents this retention in the canonical doc itself (one parenthetical in §4b / §4c if needed at edit time, otherwise treated as already-correct prose).
