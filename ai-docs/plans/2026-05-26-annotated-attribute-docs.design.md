# Design: Documentation for annotated fields / fns + attribute rename + tri-state diagnostic

**Issue:** #564
**Date:** 2026-05-26

## Approach

The work splits into four orthogonal streams that share a single rename anchor:

1. **Convention edits** (`ai-docs/doc-convention.md`, `ai-docs/code-style.md`) — add two new sections. Done first so subsequent reviewers (human + design-review) have the convention text to point at while we lift visibility and add docs. Trivially reversible if blockers surface.
2. **Macro attribute rename** (`#[prop]` → `#[property]`, `#[invokable]` → `#[invoke]`) — a mechanical sweep across `quartzite-macros/src/`, every workspace `src/`, `examples/`, `tests/`, `benches/`, doctests inside `///` / `//!` blocks, and proc-macro `attributes(prop, signal)` / `extract_attr(..., "invokable")` ident-strings. **Done immediately after convention edits and before doc-add / visibility-lift work**, so every doc summary written subsequently can use the post-rename names without a second pass. AGENTS.md § API Stability sanctions a clean break (no `#[prop]` / `#[invokable]` compat aliases retained).
3. **Spec-table re-audit + visibility lift + doc-add pass** — for every `#[base]` / `#[widget_children]` site **listed in the amended spec § *Concrete cases* table** (10 lift-needing rows after Spec Amendment round 1 dropped the already-`pub`-and-documented `EventLoop::base` and `ScrollArea::content_widget` entries), promote the field to `pub` and add a `///` doc paragraph that matches the new doc-convention § *Annotated items* template. Same PR. A pre-implementation audit step (subtask 3.5) re-verifies the amended table against HEAD before any source edit lands — so drift caught at audit time becomes a Spec Amendment **before** subtasks 4/5 execute, not after. Visibility lift is mechanical (Extend codegen reads `self.<base>` and is visibility-agnostic, confirmed by `Timer::base` already being `pub`).
4. **Tri-state macro diagnostic (`allow` / `warn` / `deny`) + three-scope cascade + fixture** — extend `quartzite-macros/src/{object,object_impl,object_part,extend}/parse.rs` to record per-annotated-item `doc-present?` and emit, at expansion time, one of three outcomes based on the resolved cascade level:
   - **`allow`** — nothing emitted.
   - **`warn`** (default) — synthesised `#[deprecated]` item with `quote_spanned!`-pointed span (per KD1).
   - **`deny`** — synthesised `compile_error!("...")` invocation with `quote_spanned!`-pointed span (per KD1).

   The cascade resolves per KD8 (per-item > per-invocation > global > built-in default `warn`) using a small helper in `quartzite-macros/src/util.rs` (per subtask 6). The opt-out / opt-in ident surface is a **registered helper attribute** `#[undocumented(allow|warn|deny)]` (per-item) plus per-invocation key-value arguments on `#[object_impl]` / `#[object_part]` / `derive(Object)` / `derive(Extend)` (per KD2). Global scope reads cargo features on `quartzite-macros` (`undocumented-allow` / `undocumented-deny`, mutually exclusive) and the env var `QUARTZITE_UNDOCUMENTED=allow|warn|deny` evaluated via `option_env!` **at compile time of `quartzite-macros` itself** (per KD9 — option (i)). The negative-test fixture uses **`trybuild`** as a new dev-dependency (see KD7 for the rationale).

### Key Decisions

| # | Decision | Rationale |
|---|---|---|
| KD1 | **Emission vehicles, level-keyed:** (a) **`warn`** — synthesised `#[deprecated = "..."]` const inside a per-type hidden mod, called once. Span pinned via `quote_spanned! { field.ident.span() => ... }` (or `method.sig.ident.span()` for `#[slot]` / `#[invoke]`) so rustc highlights the user-visible field/method, NOT the macro-synthesised hidden mod. (b) **`deny`** — synthesised `compile_error!("Annotated item `Type::field` is missing /// documentation. Opt out via #[undocumented(allow)] or set the lint level to warn/allow via #[object_impl(undocumented = \"warn\")] or feature `undocumented-allow`.")` invocation, also emitted via `quote_spanned! { field.ident.span() => ... }` so the diagnostic carat points at the user field/method, not the macro-internal `compile_error!` site. (c) **`allow`** — nothing emitted (zero codegen). All three are macro-expansion-time decisions based on the resolved cascade level — there is no runtime branch. **Open question on `warn` vehicle:** whether `#[deprecated]` actually fires the lint when the deprecated `const fn` is defined and immediately invoked in the same macro-expansion unit is not a documented stable contract. Subtask 5.5 (the **probe**) confirms this empirically before subtask 6 lands; if the probe fails, the fallback is the sibling-`pub fn` shape named in subtask 5.5's *Fallback* paragraph. **Probe landed 2026-05-26: `const _:` shape fires lint ✓** — `cargo build -p quartzite-macros --tests` with `#![deny(deprecated)]` + `const _: () = { __probe(); };` failed with `error: use of deprecated function __probe: probe-msg` at the call site. Subtask 6(c) uses the `const _: () = { __quartzite_warn_<ident>(); };` codegen shape. | `deprecated` is stable rustc lint, warn-by-default, visible during `cargo build` without `-D warnings`-gating, survives 1.x rustc upgrades. `compile_error!` is the stable mechanism for hard macro errors and inherits the `quote_spanned!`-supplied span. **Rejected** for warn vehicle: `#[diagnostic::on_unimplemented]` (fires only on trait-bound failure); custom lints via `clippy_utils` (requires nightly + workspace lint plumbing); new `must_use` chains (semantically wrong). **Span rationale (both vehicles):** without `quote_spanned`, rustc would point at the macro-internal hidden mod / `compile_error!` site instead of the user's field/method. The user-visible carat MUST be `field.ident.span()` / `method.sig.ident.span()`. **Two vehicles, not one shared:** `compile_error!` is hard-error and unsuppressible (the user cannot `#[allow]` it), which is exactly the desired `deny` semantics; `#[deprecated]` is warn-by-default and **is** `#[allow(deprecated)]`-able (acknowledged as R7), which is the desired `warn` semantics — sharing a vehicle would lose one or the other property. **Probe rationale:** rustc deduplication behaviour for same-expansion def+use of `#[deprecated]` is not in the reference; subtask 5.5 confirms-or-falsifies before the implementation commits to this shape (R10). |
| KD2 | **Opt surface: tri-state `#[undocumented(allow|warn|deny)]` per-item helper attribute + tri-state per-invocation key-value argument `#[object_impl(undocumented = "allow|warn|deny")]` / `#[object_part(undocumented = "...")]` / `#[derive(Object)] #[object(undocumented = "...")]` / `#[derive(Extend)] #[extend(undocumented = "...")]` on the enclosing macro invocation.** The per-item helper attribute takes a **single ident argument** (`allow` / `warn` / `deny`) — bare `#[undocumented]` (no argument) is rejected as ambiguous. The per-invocation form uses **key-value** (`undocumented = "allow"`) embedded in an existing attribute macro's arg list. The per-item helper is registered by adding `undocumented` to every `attributes(...)` list on the two derives (`derive(Extend)` at `quartzite-macros/src/lib.rs:63`, `derive(Object)` at `:103`). For `#[object_impl]` / `#[object_part]` attribute macros, the inert attribute is parsed inside the macro body (no `attributes(...)` change needed). For `derive(Object)` / `derive(Extend)` per-invocation, the design adds sibling derive-helper attributes `#[object(...)]` / `#[extend(...)]` registered via the same `attributes(...)` list (already a standard derive sibling-attribute pattern, e.g. `serde`'s `#[serde(...)]`). | (a) **Syntactic asymmetry justification:** per-item attribute is a registered helper occupying its own ident namespace, so a single ident argument (`#[undocumented(allow)]`) parses cleanly with `parse_nested_meta` — this matches rust's native `#[allow(dead_code)]` syntax. Per-invocation embeds inside an existing attribute macro's arg list whose grammar already uses key-value pairs (`#[object_impl(some_key = "value")]`), so `undocumented = "allow"` slots in without ambiguity. The two surfaces have different grammar constraints; trying to unify them (e.g. forcing per-invocation to take a bare ident) would conflict with the existing key-value parsing convention. (b) The string-valued form (`"allow"` instead of bare `allow`) matches `serde`'s convention for derive-sibling key-value args. (c) Per-field escape hatch + per-invocation block switch + global override exhaust the three-scope spec mandate. (d) **Per-field vs per-invocation resolution** (promoted from former Open question): both apply — per-field for granular escalate/silence inside any annotated structure, per-invocation on every macro flavour (incl. derives via `#[object(...)]` / `#[extend(...)]` sibling attributes). KD7 fixtures exercise every combination. |
| KD3 | **Ordering: convention edits → rename → spec-audit + doc-add / visibility-lift → tri-state diagnostic.** | (a) Convention text first so reviewers can audit doc summaries against a stable convention. (b) Rename second so all summary lines and doctest fixtures use post-rename names — avoids a churn round. (c) Spec re-audit (subtask 3.5) before lift edits so any drift is converted to a Spec Amendment **before** mechanical lift work, not discovered mid-edit. (d) Doc-add / visibility-lift third — the bulk of the inventory work. (e) Tri-state diagnostic last so it does not gate any of the preceding cargo builds with spurious "missing doc" warnings on items the rename pass hasn't yet touched. The default cascade level is `warn`, so a premature land would only emit warnings (not block CI under `-D warnings` since the default is just `warn`, not `deny` — but warnings still surface as noise during the rename / lift work). |
| KD4 | **`#[base]` field renames left out of scope (e.g. `widget_base` → `base`).** | Field rename is orthogonal to visibility lift and doc-add — touches every constructor (`WidgetBase::new`, `Label::new`, etc.) and every accessor inside Extend codegen. Spec § *Out of scope* says "no behavioural changes to `WidgetBase`, `Container`, etc.". Field names stay as-is (`widget_base`, `object`, `object_base`, `base`). |
| KD5 | **Use of `///` doc on private fields is supported.** | Rust accepts `///` on private struct fields. The new doc-convention § *Annotated items* explicitly overrides the existing pub-only exemption when any inventoried attribute is present. The `missing_docs` workspace lint doesn't fire on private fields, but the new tri-state diagnostic from KD1 takes over that role. |
| KD6 | **Macro-side doc detection: `attr.path().is_ident("doc")` on the field / fn attribute list, after attribute extraction.** Look at the field/fn's preserved attrs in `parse.rs`; if no `doc` attr is present and the resolved cascade level is `warn` or `deny`, emit the corresponding vehicle (per KD1). | `///` desugars to `#[doc = "..."]` before proc-macros run, so checking `attrs` is the correct surface. Per-field flag in `PropField` / `SignalField` / `MethodItem` / `BaseField` / `MixinField` / `WidgetChildrenField` is the cleanest carrier. The flag is `doc_present: bool` (a single bool), and the resolved cascade `Level` is computed alongside it. |
| KD7 | **Test fixture format: `trybuild` integration test under `quartzite-macros/tests/`.** Add `trybuild = "1"` to `quartzite-macros/Cargo.toml` `[dev-dependencies]`. The `compile_fail` directory holds the `deny`-engaged fixtures (paths (f), (g) per AC7); the `pass` directory holds every other fixture, including the `warn`-fires fixture which uses `#![deny(deprecated)]` at the top of the file to convert the `deprecated` lint into a hard error inside trybuild's compile-fail run — i.e. the `warn`-fires path is asserted by **inverting** it via `#![deny(deprecated)]` and placing the result under `compile_fail/` (since the `deprecated` lint, when escalated to error via `#![deny]`, surfaces exactly like a real error and trybuild captures the stderr). The cleaner split: `compile_fail/` for (a)-via-`#![deny(deprecated)]`, (f), (g); `pass/` for (b), (c), (d), (e), (h). | `trybuild` is the canonical mechanism for "verify proc-macro emits this exact diagnostic" and is mentioned in AC7. New dev-dep cost is low (`trybuild` is a one-line `[dev-dependencies]` addition). **`#![deny(deprecated)]` trick** to assert warn-fires inside `compile_fail/`: trybuild requires a real compile failure to compare stderr — escalating `deprecated` to `deny` at the fixture's top is the standard ecosystem pattern (used by `serde_derive` tests, `pin-project` tests). |
| KD8 | **Cascade precedence: per-item > per-invocation > global > built-in default (`warn`). Resolution algorithm walks scope-by-scope at expansion time; first non-`None` wins.** Implemented as a helper in `quartzite-macros/src/util.rs`: `fn resolve_undocumented_level(per_item: Option<Level>, per_invocation: Option<Level>) -> Level`. Global scope (env var + cargo features) is read ONCE per expansion via a separate helper `fn global_undocumented_level() -> Option<Level>` and passed as the third tier. **Worked example:** an `#[object_impl(undocumented = "deny")]` block contains two annotated methods — method `foo` carries `#[undocumented(allow)]`, method `bar` carries nothing. Resolution: `foo` → `Some(Allow)` (per-item wins) → `allow` → no emit. `bar` → `None` per-item, `Some(Deny)` per-invocation → `deny` → emit `compile_error!`. Sibling methods inside the same block receive different treatment, exactly per rust's `#[allow]` precedence. | Mirrors rust's native lint cascade (item > module > crate > default), which the spec mandates. Centralising the resolution in a single fn lets subtask 6 unit-test the precedence in isolation, and any future addition of a fourth scope (e.g. workspace-config file) drops in as one more `Option<Level>` argument without touching codegen call sites. |
| KD9 | **Global scope surface: cargo features `undocumented-allow` and `undocumented-deny` on `quartzite-macros` (BOTH may be active simultaneously — `deny` wins, mirroring rust's lint-level precedence where the strictest setting prevails); environment variable `QUARTZITE_UNDOCUMENTED=allow\|warn\|deny` read via `option_env!("QUARTZITE_UNDOCUMENTED")` AT COMPILE TIME OF `quartzite-macros` ITSELF (NOT at proc-macro expansion time in user crates). Env var beats cargo feature (but is still below per-invocation and per-item).** Resolution order inside `global_undocumented_level()`: `option_env!("QUARTZITE_UNDOCUMENTED")` first; if `Some(s)` + `s` parses to a valid level, return; else `cfg(feature = "undocumented-deny")` → `Deny`; else `cfg(feature = "undocumented-allow")` → `Allow`; else return `None` (falls through to built-in default `warn`). **Step 11 amendment (Round 1 fix #3):** the earlier draft mandated a `compile_error!` mutex when both features were active — discarded because workspace `cargo doc --all-features` activates every feature simultaneously, which would always fire the mutex error. Replaced with deterministic precedence (`deny` wins) — preserves "loud about misconfig" intent in spirit (the stricter setting is chosen) without breaking the standard doc gate. Single-config users still get exactly one feature active; precedence only matters under `--all-features`. **Documented contract:** to change the env-var-driven global level, the `quartzite-macros` crate MUST be rebuilt (e.g. `cargo clean -p quartzite-macros && QUARTZITE_UNDOCUMENTED=allow cargo build`). Cargo incremental compilation re-runs `option_env!` evaluation only when the `quartzite-macros` crate is itself recompiled. | **Why `option_env!` over `std::env::var` (option (i) from the round-2 feedback chosen):** `std::env::var` at proc-macro expansion time is **not** tracked by Cargo's dependency graph — Cargo will not invalidate proc-macro consumers when the env var changes between runs, so user crates would see stale levels until manually cleaned. `option_env!` evaluates at compile time of the proc-macro crate, baking the value into the macro binary; the "rebuild quartzite-macros to change the level" trade-off is documented and incremental-safe. **Rejected: option (ii)** `std::env::var` + `build.rs` `rerun-if-env-changed` — Cargo's env-var-tracking does NOT propagate through proc-macro boundaries, so user crates may still see staleness even with `rerun-if-env-changed`; the contract becomes "rebuild quartzite-macros + every user crate", which is worse than option (i)'s clean "rebuild quartzite-macros only". **Rejected: option (iii)** `proc_macro::tracked_env::var` — gated behind unstable `tracked_env` feature, requires nightly toolchain; nightly-only is incompatible with the workspace's stable-toolchain posture. **Env-var-over-feature rationale:** lets one-off rebuilds of the macro crate override without editing `Cargo.toml`. Example: `cargo clean -p quartzite-macros && QUARTZITE_UNDOCUMENTED=allow cargo build` for a one-shot refactor pass, without committing a feature-flag change. **Precedence-over-mutex rationale:** the earlier draft used a `compile_error!` mutex, but workspace `cargo doc --all-features` enables every feature including both `undocumented-allow` and `undocumented-deny`, which would always fire the mutex error and break the doc gate. Replaced with `deny`-wins precedence so the strictest setting prevails when both are active — consistent with rust's native lint-level precedence, doc-gate-safe, and still single-valued. **Feature naming rationale:** `undocumented-allow` / `undocumented-deny` follow the existing kebab-case convention for cargo features and self-document the lint-level vocabulary. No `undocumented-warn` feature — `warn` is the default; users wanting `warn` simply omit both features. |

## Risks

- **R1 — Tri-state diagnostic's default-`warn` accidentally upgrades to error under `-D warnings` in CI.** The workspace runs `cargo clippy --workspace --all-targets -- -D warnings` and `RUSTDOCFLAGS="-D warnings -D missing-docs" cargo doc`. The synthesised `#[deprecated]` must be visible during `cargo build` (default warn) yet NOT under `-D warnings`-gated CI. **Mitigation:** the in-scope inventory is fully documented by Group B before the tri-state diagnostic lands in Group C subtask 6, so when CI runs `-D warnings`, every annotated item already carries `///`. Re-verify in subtask 7 that no warning fires across the workspace. **Fallback:** hot-fix by either adding the missing `///` or engaging the per-item `#[undocumented(allow)]` opt-out — both are seconds-to-apply.
- **R2 — Doctests / `//!` examples retain `#[prop]` / `#[invokable]` after the rename sweep and silently break the rename invariant.** **Mitigation:** the AC6 grep uses `#\[prop\b\|#\[invokable\b` which catches attribute syntax inside any text — `//!` doc bodies, doctest fences, `///` blocks, inline comments. Subtask 3 explicitly enumerates `src/lib.rs` `//!` blocks as in-scope.
- **R3 — Spec § *Concrete cases* table drift between amendment time and implementation time.** **Mitigation:** dedicated subtask 3.5 re-audits the table against HEAD before any lift edit lands; any drift becomes a Spec Amendment per the recipe in `.claude/skills/task/SKILL.md` Step 7.
- **R4 — Per-invocation `(undocumented = "...")` argument on `#[object_impl]` / `#[object_part]` / sibling `#[object(...)]` / `#[extend(...)]` collides with existing argument parsing.** The `#[object_impl]` / `#[object_part]` parsers currently reject any non-empty attribute body with "use `#[object_part]` for accumulating blocks". The derive-sibling `#[object(...)]` / `#[extend(...)]` are new — no collision but must be wired through `attributes(...)` lists per subtask 2. **Mitigation:** extend `object_impl::parse::parse` to permit exactly `undocumented = "<value>"` as a sole nested-meta token; same shape on `object_part::parse::parse`. Sibling `#[object(...)]` / `#[extend(...)]` are pure additions parsed inside the derives' input-walk (per subtask 6 (b) parse-mechanism note). Covered by AC7 fixtures (d) and (g).
- **R5 — Documentation of `WidgetBase::object` (`pub object: ObjectBase`) creates a public-API surface that downstream framework users could rely on, locking in the field name.** Pre-publish AGENTS.md § *API Stability* sanctions arbitrary renames; the rename concern is non-blocking pre-`cargo publish`.
- **R6 — Doc-comment summary lines drift from the convention added in subtask 1.** **Mitigation:** the new `## Annotated items` section in `doc-convention.md` carries a single common summary-line template (per the KD-default in spec § *Open questions* item 3). Each doc summary in subtasks 4 / 5 lifts wording verbatim from that template.
- **R7 — `#[deprecated]` warning silenced by user-side `#[allow(deprecated)]` for unrelated reasons.** A downstream crate that wraps a stdlib `#[deprecated]` call site with `#[allow(deprecated)]` (a common pattern when migrating away from a stdlib deprecation) will silently silence Quartzite's annotated-doc nudge if both happen to be in scope of the same `#[allow]`. **This risk only affects the `warn` level** — `deny`-level users get `compile_error!` which is unsuppressible (cannot be `#[allow]`'d). **Mitigation:** documented here as a known false-suppression vector for the `warn` level only; no in-PR fix. The nudge is best-effort and the workspace `missing_docs = "deny"` already covers the public-API surface — annotated-but-non-public items remain a soft target. **Fallback:** users hitting false suppression can opt the affected scope (per-invocation or per-item) up to `deny` to convert the lint into an unsuppressible `compile_error!`; the tri-state model gives this exact escape hatch by design.
- **R8 — Global-scope env var vs cargo feature interaction surprise (CI confusion).** The cascade reads env var `QUARTZITE_UNDOCUMENTED` BEFORE cargo features (per KD9), so a CI run with `--features quartzite-macros/undocumented-deny` set AND the env var unset uses `deny`; the same run with `QUARTZITE_UNDOCUMENTED=warn` exported in the shell at the time `quartzite-macros` was last compiled silently overrides the feature and uses `warn`. Devs reading the `Cargo.toml` feature list may not realise an env var baked at the macro-crate's compile time is winning. **Mitigation:** the precedence is documented in `doc-convention.md` § *Annotated items* (subtask 1) AND in the `compile_error!` message emitted by `Level::Deny` (subtask 6) — the message hint "or set the lint level to warn/allow via …" enumerates both surfaces so the dev sees both paths. **Fallback if confusion materialises:** add an `#[diagnostic::do_not_recommend]`-style note or emit an info-level diagnostic when env var and feature both set and disagree (out of scope for v1; would need either nightly diagnostic API or a separate `compile_error!`-on-disagreement branch in `global_undocumented_level()`).
- **R9 — Env-var staleness across rebuilds (`option_env!` semantics).** Per KD9, `QUARTZITE_UNDOCUMENTED` is read via `option_env!` at compile time of `quartzite-macros` itself, NOT at proc-macro expansion time in user crates. **Implication:** changing the env var has NO effect on user crates until `quartzite-macros` is rebuilt — Cargo incremental compilation will skip rebuilding `quartzite-macros` if no Rust source has changed. **Mitigation:** the documented contract (KD9 + `doc-convention.md` § *Annotated items*) is "rebuild `quartzite-macros` to change the env-var-driven global level": `cargo clean -p quartzite-macros && QUARTZITE_UNDOCUMENTED=allow cargo build`. **Trade-off vs alternatives:** option (ii) (`std::env::var` + `build.rs` `rerun-if-env-changed`) was rejected because env-var-tracking does NOT propagate through proc-macro boundaries — user crates may still see staleness even with `rerun-if-env-changed` set, which is a worse contract than option (i)'s clean "rebuild quartzite-macros only". Option (iii) (`proc_macro::tracked_env::var`) is nightly-only (unstable `tracked_env` feature) and incompatible with the workspace's stable-toolchain posture. **Why this is acceptable:** the env var is primarily a one-off CI / developer override; the common case is "set the cargo feature in `Cargo.toml`" (which Cargo's dep graph correctly invalidates). The env var path is documented as "ephemeral + requires explicit rebuild" and reserved for one-shot pass-through; subtask 7's AC7 path (e) fixture exercises the cargo-feature path (not env var) for this reason — see subtask 7 fixture (e).
- **R10 — `#[deprecated]` lint may not fire at same-expansion def+use site.** The `deprecated` lint fires when a user references a deprecated item, not on its definition. The synthesised `const fn __quartzite_warn_<ident>` definition + immediate `const _: () = { __quartzite_warn_<ident>(); };` invocation both originate inside the SAME proc-macro expansion, even with `quote_spanned!` re-spanning the call. Whether rustc dedupes same-expansion def+use (suppressing the lint) is NOT a documented stable contract — undocumented rustc internals may treat both nodes as part of the same expansion unit and skip the lint check. **Mitigation:** subtask 5.5 lands a 30-line probe that empirically confirms-or-falsifies the assumption BEFORE subtask 6's codegen lands. **Fallback (named in subtask 5.5):** if the probe shows the lint doesn't fire under the `const _:` shape, emit a sibling `pub fn __quartzite_doc_check_<ident>()` adjacent to the annotated struct (at module level, NOT inside a `const _:` block) that calls the deprecated fn from a different syntactic context — the different-span sibling-fn shape forces rustc out of any same-expansion dedup heuristic. The probe's verdict is recorded inline in KD1's rationale as a one-line addendum, so the implementation choice is auditable.

AC7 verbatim from amended spec, for the implementer's reference:

> The proc macros emit a tri-state diagnostic (`allow` / `warn` / `deny`) at expansion time per scope item 7. Default level is `warn`. A workspace test under `quartzite-macros/tests/` (`trybuild` recommended for the `deny`-engages-error path; warnings-captured fixture or compile-only test capturing rustc stderr for the others) covers **every level at every scope** — at minimum: (a) `warn` fires when doc is missing (default, no override); (b) silent when doc is present (default, no override); (c) per-item `allow` silences a missing doc; (d) per-invocation `allow` silences a block of missing docs; (e) global `allow` (via cargo feature or env var) silences all; (f) per-item `deny` escalates a missing doc to compile error (`trybuild` compile-fail fixture); (g) per-invocation `deny` escalates a block; (h) most-specific-wins cascade (per-item `allow` overrides per-invocation `deny`, etc. — at least one fixture demonstrating the precedence). `cargo build` succeeds for paths (a)–(e) and (h)-allow-cases; paths (f)–(g) and (h)-deny-cases are compile-fail fixtures. All tri-state surfaces (per-item attribute name, per-invocation attribute name, cargo feature name, env var name) are documented in `doc-convention.md` § *Annotated items*.
